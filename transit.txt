# opentest-design

> **`$SKILLS_DIR`** — каталог, где лежат все навыки `opentest-*`. Пример: если этот файл — `.opencode/skills/opentest-new-test/SKILL.md`, то `$SKILLS_DIR` = `.opencode/skills/`.

## Steps

### 1. Определить цель

Поиск в двух каталогах:

**Spec-mode (baseline):**
```bash
ls opentest/tests/ 2>/dev/null
```

**Change-mode (тест-чейндж):**
```bash
ls opentest/testchanges/ 2>/dev/null | grep -v archive
```

Если имя указано — искать сначала в `testchanges/`, затем в `specs/`.

Если имя не указано:
- Объединить списки из обоих каталогов
- Если только один вариант — использовать его
- Если несколько — предложить выбор через AskUserQuestion, указав режим (spec/change) и путь
- Если ничего не найдено — отказ: «Нет baseline и нет активных test changes. Сначала запустите opentest-new-test или opentest-propose.»

Объявить: "Проектирую доработку тестов для <name> (режим: <change|spec>)"

**Определение режима по test.md:**
- Содержит `> **Статус**:` → change-режим
- Содержит `> **Режим**: spec` → spec-режим

### 2. Проверить наличие артефактов

Прочитай `test.md` по найденному пути.

**Если test.md не существует:** предложи сначала запустить `opentest-new-test` (spec-режим) или `opentest-propose` (change-режим) для генерации спецификации тестов.

**Для spec-режима** (`> **Режим**: spec`) — статус не проверяется. Продолжай сразу (шаг 3).

**Для change-режима** (`> **Статус**:`) — проверь статус:

| Статус | Действие |
|--------|----------|
| `Согласовано` | OK, продолжать. Design для change-mode. |
| `В реализации` | OK, продолжать (возможно, повторный запуск design для корректировки). |
| `На согласовании` | **Блок**: test change не согласован. Сообщи: «Поставь статус "Согласовано" вручную после ревью.» Выйти. |
| `Реализовано` | Сообщи, что тесты уже реализованы. Спроси: обновить design или выйти. |
| `Архивировано` | Сообщи, что change уже архивирован. Выйти. |

**Если design.md уже существует:** режим (продолжить vs создать заново) определяется на шаге 2.7 по наличию Change Manifest. Не спрашивай пользователя сейчас — шаг 2.7 решит.

### 2.7. Read Change Manifest (определение режима)

Прочитай `.research/upstream-changes.yaml` в базовом пути (создаётся `opentest-new-test` / `opentest-propose` в correction-режиме, см. §4.4 соответствующего навыка).

**Определение режима:**

| Состояние | Режим | Действие |
|-----------|-------|----------|
| Manifest присутствует (history непустой) | **Correction** | Продолжить редактирование design.md. Подтверди yes/no: «Обнаружен Change Manifest с N записей. Продолжаю в correction-режиме (skip as-is research, Partial/Phrases update по Decision Matrix). ОК?» |
| Manifest отсутствует + design.md существует | **Full run (продолжить)** | Спроси yes/no: продолжить редактирование или создать заново |
| Manifest отсутствует + design.md не существует | **Full run (новый)** | Продолжай без вопросов |

**Decision Matrix (применяется в последующих шагах 3–7):**

| Изменение в manifest | Действие design |
|---|---|
| `features/**` | **Partial update**: перечитать изменённые файлы (шаг 3), обновить §3, §6a, §7 design.md. Skip 4 (cross-check) если архитектура не изменилась |
| `phrases.yml` с `new_ids` | **Phrases update**: Partial + §2.2.1 delta-phrases (новые ID) + §2.3 regenerate (шаг 8) + новая задача в tasks.md |
| `phrases.yml` без `new_ids` | **Phrases update**: Partial + §2.2.1 (изменяемые фразы) + §2.3 regenerate (шаг 8) |
| Manifest пуст / только `user-feedback` | **Verify-only**: skip 2.5, 3, 4, 5, 6; только §8 regenerate + §9 ревью |
| Manifest отсутствует | **Full run** (включая 2.5, 3, 4, 5, 6, 7, 8) |

> **Несколько типов изменений** в одной записи manifest — суммируются. Например, `features/` + `phrases.yml` с `new_ids` → Partial + Phrases update (выполняются обе ветки).

**Skip 2.5 as-is research:** в correction-режиме (manifest present) — skip **безусловно**. Основание: new-test трогает только features/fixtures/phrases — тестовая инфраструктура (step definitions, конфиги, pom.xml, фреймворк) не меняется. Переиспользуй существующий `.research/test-architecture-as-is.yaml` + `.md`.

**Отслеживание обработанных записей:** прочитай `.research/design-state.yaml` (если существует). Сравни `last_manifest_entry_processed` с `date` записей в manifest. Обрабатывай только записи с `date > last_manifest_entry_processed`. Если state-файл отсутствует — обрабатывай все записи manifest (как при первом correction-ране).

### 2.5. Исследуй архитектуру тестов as-is (через `opentest-explore`)

> **Correction-режим (manifest present):** SKIP этого шага безусловно. Тестовая инфраструктура не меняется при правках features/fixtures/phrases. Переиспользуй существующий `.research/test-architecture-as-is.yaml` + `.md`. Переходи к шагу 3.

**Дизайн исследует ТОЛЬКО текущую архитектуру тестов.** Архитектура сервиса и контракты уже исследованы на этапе propose/new-test. Дизайн на основе as-is тестовой архитектуры и входных артефактов (feature-файлы, phrases.yml) формирует `design.md` — целевое состояние подсистемы тестирования (фреймворк, моки, step definitions, фикстуры).

**Порядок:**
1. Прочитай `$SKILLS_DIR/opentest-explore/references/invocation-contract.md` — освоить контракт
2. Прочитай `$SKILLS_DIR/opentest-explore/references/research-orchestration.md` — группировка: `target=design`, `service=<имя>`
3. Прочитай `$SKILLS_DIR/opentest-explore/references/research-roles.md` — взять промпт роли `test-architecture-as-is`
4. Обнаружь tool запуска субагента по алгоритму § 3.1 invocation-contract.md
5. Адаптируй плейсхолдеры путей под стек (invocation-contract.md § 5)
6. Запусти **один** субагент:

**Роль: test-architecture-as-is**
- Роль `test-architecture-as-is`
- Scope: директории тестов, step definitions, конфигурации
- Промпт дословно из research-roles.md, пути подставлены

**После возврата:**
7. Запиши YAML в `.research/test-architecture-as-is.yaml`
8. Валидируй YAML (§ 6 invocation-contract.md)
9. Запиши `.research-notes.md` (обнови существующий или создай)
10. Создай документ `test-architecture-as-is.md` на основе YAML

**Формат test-architecture-as-is.md:**

### 3. Изучи артефакты

**КРИТИЧЕСКИ: НЕ изменяй, не переименовывай, не удаляй и не переписывай feature-файлы и phrases.yml.** Это входные данные, созданные на этапе new-test. Design ТОЛЬКО читает их и создаёт design.md + tasks.md на их основе. Любые структурные изменения (переименование, разделение, объединение, удаление файлов) — только через явное согласие пользователя на шаге 4.

**Зафиксируй снэпшот для верификации на шаге 6b:**

**Базовый путь:**
- Spec-mode: `opentest/tests/<service>/`
- Change-mode: `opentest/testchanges/<name>/` + baseline `opentest/tests/<service>/`

Прочитай все доступные артефакты в базовом пути и зафиксируй:

- **Feature-файлы**: <список имён с количеством сценариев> (например: `create-release.feature` (6), `domain-services.feature` (5), ...)
- **phrases.yml**: GC-001...G-XXX (N штук), WC-001...W-XXX (N штук), TC-001...T-XXX (N штук) — точные ID как в файле
- **Timestamp'ы**: запомни время модификации feature-файлов (для проверки, что они не изменились)

**Для change-mode — ДОПОЛНИТЕЛЬНО прочитай baseline:**
- `opentest/tests/<service>/test.md` — текущее покрытие (архитектура тестовой подсистемы выбирается в design из reference-архитектуры `java-cucumber-spring`)
- `opentest/tests/<service>/phrases.yml` — baseline фразы (для понимания существующих step definitions и ID-continuation)
- `opentest/tests/<service>/features/*.feature` — существующие сценарии

**Для change-mode — зафиксируй delta-снэпшот:**
- Delta features: список имён с количеством сценариев
- Delta phrases: диапазон новых ID (G-XXX..G-YYY), список reused baseline ID
- Baseline phrases max IDs: для проверки ID-continuation в design

a. **`test.md`** — паспорт изменения:
   - Краткое описание изменения
   - Архитектура тестовой подсистемы выбирается в design из reference-архитектуры `java-cucumber-spring`
   - Требования к доработке подсистемы тестирования
   - Ссылки на контракты
   - Перечень feature-файлов

b. **Все `.feature`-файлы** в `features/` — понять scope сценариев

c. **`phrases.yml`** — понять текущий справочник фраз

d. **`.research/test-architecture-as-is.md`** — as-is архитектура тестов (создана на шаге 2.5):
   - Текущий фреймворк и структура тестов
   - Конфигурация моков
   - Управление фикстурами
   - Интеграция в билд

e. **`.research/interview-decisions.yaml`** — решения интервью: исключённые UC, DB Write Approval

f. **`features/<feature-name>/`** — файлы тестовых данных (CSV, JSON), созданные на этапе new-test/propose. Включая `features/<feature-name>/expected/` (schema-фикстуры ответов), `features/<feature-name>/db/` (schema-фикстуры DB-записей), `features/<feature-name>/queries/` (SQL для TC-007), `features/<feature-name>/mock/` (mock-ответы партнёров)

g. **`.research/user-provided-contracts.yaml`** — пользовательские данные о контрактах (если есть, из gap resolution шага 4.6 new-test)

> **Архитектурный контекст (моки, БД, интеграции)** берётся из двух источников: (1) `features/*.feature` — шаги содержат mock-setup фразы (GC-001..GC-003), mock-verify (TC-002), DB-check (TC-005..TC-007, delta T-*), Kafka asserts (TC-008, TC-009, delta T-1*); (2) `.research/test-architecture-as-is.{yaml,md}` (шаг 2.5) — существующая тестовая инфраструктура. Бизнес-контекст спецификации (обработчики, ошибки, FSM, бизнес-правила) — в самих feature-файлах (Scenario titles, Then-шаги). Архитектура тестовой подсистемы выбирается в design из reference-архитектуры `java-cucumber-spring`.
>
> **Для change-mode:** пункты a-g читаются из testchanges. Baseline читается дополнительно для понимания существующих step definitions и переиспользуемых canonical фраз.

### 3a. Алгоритм вывода: спецификация → конкретные решения

На основе прочитанных артефактов выведи конкретные технические решения. Каждый вывод — воспроизводимое правило, не интуиция.

**Моки (design.md §1.2):**

| Вход | Правило | Выход |
|---|---|---|
| `features/*.feature` → mock-setup фразы (GC-001, GC-002, GC-003) + mock-verify (TC-002) | Для каждого партнёра (имя из mock-фразы / имени mock-фикстуры) — создать `<Name>MockServer.java` (или entry в `DomainMockServer` Map) | Таблица мокирования: сервис, инструмент, порт, env-переменная, контракт |
| `features/<feature-name>/mock/*.json` (имена файлов и структура ответов) + контракты партнёров (если есть в `.research/user-provided-contracts.yaml` или `features/*.feature`) | Для каждого мока — перечислить фикстуры ответов из `features/<feature-name>/mock/` | Список фикстур мока |
| `test-architecture-as-is.yaml → mocks → timeout` (если есть) или значение по умолчанию | Timeout для HTTP-вызовов моков | application-test.yml: connect/read timeout |

**БД (design.md §1.2 маппинг типов + isolation):**

| Вход | Правило | Выход |
|---|---|---|
| `features/<feature-name>/db/*.json` (schema-фикстуры DB-записей — содержат имена колонок) + DDL/контракты по ссылке из `features/*.feature` (если доступно) | Для каждой колонки с типом JSONB, UUID, bigint — добавить в colType mapping | Таблица маппинга типов БД |
| `features/*.feature` → DB-check фразы (TC-005, TC-006, TC-007, TC-010, delta T-*) + seed side-effects (GC-004/GC-005 создают записи через API) | Все таблицы из DB-check шагов ∪ таблицы, в которые GC-004 seed создаёт записи, — добавить в `cleanup_tables` (confirmation-список из `interview-decisions.yaml`) → `test.db.clean-tables` | Список таблиц для очистки |
| `features/<feature-name>/db/*.json` + `features/<feature-name>/expected/*.json` (schema-фикстуры) | Свериться с schema-фикстурами, созданными в `opentest-new-test`. Если для ключевого сценария schema-фикстуры отсутствуют — рекомендовать пользователю добавить их через new-test/propose (format: `$options`, `${json-unit.any-*}`). Design НЕ создаёт schema-фикстуры сам | Список schema-фикстур (справочно) |
| `interview-decisions.yaml → db_write_approval` | Одобренные таблицы — разрешить INSERT в SharedData_Steps | §3.3 пометка «одобрено» |
| `interview-decisions.yaml → cleanup_tables` | Confirmation-список таблиц для `@Before(order=20)` cleanup. Набор = DB-check фразы (TC-005/006/007/TC-010, delta T-*) ∪ seed side-effects (GC-004/GC-005 создают записи). Пользователь подтверждает набор | §3.3 блок `cleanup_tables` + `test.db.clean-tables` в §1.2 |

**Конфигурация (design.md §1.3):**

| Вход | Правило | Выход |
|---|---|---|
| `features/*.feature` → WC-003 multipart file step (шаги прикрепления файлов) | Список multipart-endpoints | application-test.yml: `test.multipart-endpoints` |
| `features/<feature-name>/db/*.json` (имя схемы из DDL) или `test-architecture-as-is.yaml → currentSchema` | Имя схемы БД | application-test.yml: `currentSchema` |

**Привязка фраз к step definitions (design.md §2.3):**

| Категория фраз | Класс step definitions | Примеры ID |
|---|---|---|
| Given: DB seed (GC-007) | SharedData_Steps | Прямой SQL (INSERT/UPDATE/DELETE/ALTER SEQUENCE) |
| Given: Mock setup (GC-001, GC-002, GC-003) | SharedMock_Steps + `<Name>MockServer` | enqueue/verify |
| Given: API seed (GC-004, GC-005) | SharedHttp_Steps + SharedData_Steps | POST + capture |
| When: HTTP request (WC-001) | SharedHttp_Steps | lazy execute |
| When: Fixture body (WC-002) | SharedHttp_Steps | load from features/<feature>/ (через FixtureResolver) |
| When: Multipart file (WC-003) | SharedHttp_Steps | attachFile: fileName + explicit partName |
| Then: HTTP status (TC-001) | SharedAssert_Steps | statusCode |
| Then: Schema assertions (TC-004) | SharedAssert_Steps + SchemaAssertion | responseMatchesSchema |
| Then: DB schema (TC-005, TC-006, TC-007) | SharedDb_Steps + SchemaAssertion | row_to_json / json_agg + JsonUnit |
| Then: Mock verify (TC-002) | SharedMock_Steps | takeRequest + assert |

**Для change-mode — delta-выводы:**

| Вход | Правило | Выход |
|------|---------|-------|
| Delta phrases (новые ID) | Для каждой НОВОЙ фразы определить класс step definitions | Таблица привязки delta-фраз |

**Для change-mode:** design.md описывает ТОЛЬКО delta — что нужно добавить к существующей тестовой подсистеме. Не дублировать baseline-описание. Структура design.md та же (§1-5), но каждый раздел содержит только новые элементы.

Заполни разделы шаблона `templates/design.md` реальными данными из артефактов `opentest-new-test` (spec-режим) или `opentest-propose` (change-режим).

**Структура design.md:**
1. **Доработки подсистемы BDD-тестирования**
2. **Фикстуры для новых тестов**
3. **План доработок**
4. **Риски и ограничения**
5. **Изменения справочника фраз (phrases.yml)**

**Содержание раздела 1 (Доработки подсистемы BDD-тестирования):**
   - Выбранный фреймворк и библиотеки (версии закреплены)
      - **Logbook** — HTTP-логирование. ДОЛЖЕН быть включён в зависимостях и конфигурации. Без него отладка HTTP-взаимодействий вслепую.
      - **Custom Type Registry** — ДОЛЖЕН быть создан класс с типами `{val}` и `{path}`. `{val}` = `"[^"]*"|'[^']*'|\S+` — матчит значения с кавычками и без. `{path}` = `.*` — матчит URL-пути.
   - Настройка мокирования смежных сервисов (конкретные инструменты)
   - **Изоляция тестов** — обязательный блок. Заполни по шаблону из §1.2 шаблона design.md
   - Конфигурация запуска тестов
   - **Схема БД** — на основе schema-фикстур `features/<feature-name>/db/*.json` (содержат имена таблиц и колонок), DB-check фраз в `features/*.feature` (TC-005..TC-007, delta T-*) и DDL/контрактов по ссылке из `features/*.feature` (если доступно):
      - Имя схемы: из schema-фикстур или `test-architecture-as-is.yaml` (поле `currentSchema`)
      - Зафиксировать в `design.md` §1.3 как `currentSchema` для `application-test.yml`
   - **Маппинг типов БД** — ДОЛЖЕН быть описан для JDBC-совместимости:
      - SQL-касты `::integer`, `::bigint` НЕ РАБОТАЮТ через JDBC. Вместо них — Java-side выбор setObject-типа.
      - Для каждой таблицы перечисли колонки с нестандартными типами (jsonb, bigint, uuid).
      - Все имена колонок квотируются (`"column"`) для защиты от SQL reserved words.
   - **Docker-образы и инфраструктурные сервисы** — на основе mock-фраз в `features/*.feature` (GC-001..GC-003 — какие сервисы мокаются) и `test-architecture-as-is.yaml` (существующая инфраструктура):
      - Образ тестируемого сервиса (имя:тег), пометка «сконфигурируй при необходимости»
      - Перечень инфраструктурных сервисов (БД, Kafka) с пометкой «зона ответственности пользователя»
      - Stash (Bitbucket) и другие мокаемые сервисы НЕ включать в инфраструктурную таблицу
      - **НЕ включай DDL/инициализацию схемы БД.** Инфраструктура предоставляется пользователем в готовом виде: БД проинициализирована, схема создана.

**Содержание раздела по phrases.yml (5 для spec):**

**Фразы спроектированы на этапе new-test (Phrases-First). Design НЕ создаёт и НЕ изменяет phrases.yml.** Если дизайн обнаруживает пробел (шаг в feature не матчится на фразу, поле из schema-фикстуры или DB-check шага не проверено), это баг new-test — зафиксируй в разделе «Пробелы» и сообщи пользователю.

Раздел phrases.yml в design.md содержит:
   - **Верификацию полноты**: все ли шаги из `features/*.feature` матчатся на фразы, нет ли ambiguity, все ли поля из schema-фикстур (`features/<feature-name>/expected/`, `features/<feature-name>/db/`) покрыты DB-check шагами
   - **Привязку фраз к step definitions** — какая фраза каким классом реализуется. Это ЕДИНСТВЕННАЯ задача design по фразам: сопоставить ID из phrases.yml с классами шагов (SharedHttp_Steps, SharedAssert_Steps и т.д.).
   - **Пробелы** (если обнаружены) — что не хватает, почему это пробел propose, а не задача design.

**Правила:**
- Ссылайся на конкретные сущности из контрактов (DTO, схемы, enum-значения)
- Уровни обязательности: ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ
- Не проектируй step definitions (это `opentest-implement`), но опиши что нужно реализовать
- Удали все HTML-комментарии из шаблона
- **Используй ТОЛЬКО ID фраз из файла `phrases.yml`** (GC-001, WC-001, TC-001 как в файле на диске). Не создавай новую нумерацию. Если фраза требует изменения — укажи старый ID и новую формулировку в §2.2 (Изменяемые фразы)
- **Ссылайся на фактические имена feature-файлов** с диска (из снэпшота шага 3). Не переименовывай их в design.md

Сохрани в базовый путь как `design.md`.

### 6b. Проверь консистентность артефактов (ОБЯЗАТЕЛЬНО)

Сверь созданный design.md и tasks.md с исходными файлами на диске, используя снэпшот из шага 3:

4. **Timestamp'ы feature-файлов** — сравни с timestamp'ами из снэпшота. Если feature-файлы изменились (были перезаписаны) — немедленно предупреди пользователя: «Feature-файлы были изменены в процессе design. Это ошибка. Восстановить из git?»
5. **Проверка непротиворечивости моков и инфраструктуры (MUST)** — составь два списка:
   - Список А: сервисы, объявленные как «мокаемые» в §1.2 (таблица мокирования)
   - Список Б: сервисы в таблице «Инфраструктурные сервисы (зона ответственности пользователя)» в §1.4
   - Проверь, что пересечение списков пусто. Если сервис есть в обоих списках — это ошибка. Исправь: удали сервис из инфраструктурной таблицы (он мокается), обнови сноску.
6. **Проверка env-переменных для моков (MUST)** — для каждого мока в §1.2 проверь:
   - Указана ли env-переменная, через которую тестируемый сервис обращается к этому моку (например, `DISTR_URL=http://localhost:8081`)
   - Если не указана — добавь для каждого мока строку вида: «Сервису передаётся через env `<ИМЯ_ПЕРЕМЕННОЙ>=http://localhost:<порт>`»
   7. **Проверка state-declaration для фраз (MUST)** — для всех фраз (canonical и delta), у которых в `phrases.yml` поле State (writes) ≠ пусто, проверь, что в design.md §2.3 (phrase-mapping) они связаны с классами step definitions, которые фактически кладут значения в TestContext (через `testContext.put(...)` / аналогичный API). Gate падает, если step definition не делает того, что декларирует `phrases.yml` (фраза декларирует state-writes, но соответствующий step definition не пишет в TestContext).
    8. **Gate 7.2 (MUST):** Для каждой не-text колонки из schema-фикстур `features/<feature-name>/db/*.json` (boolean, smallint-boolean, DECIMAL, PG-array, jsonb, timestamp — по типу значения в фикстуре или DDL) в design.md §1.2 в столбце «Каст для assertQueryMatches» ДОЛЖЕН быть указан SQL-каст, приводящий значение к корректному JSON-узлу. Gate падает, если для non-text колонки каст не задан.

### 7. Создай tasks.md

На основе `design.md` и требований из `test.md`:

**Обязательные категории задач:**

1. **Инфраструктура** — тестовый модуль, pom.xml, application-test.yml, cucumber.properties
2. **Моки** — MockServer классы, фикстуры моков (перенос из features/<feature-name>/mock/)
3. **Step definitions** — Shared* классы, colType mapping, cleanTables
4. **Feature-файлы** — перенос из features/ в src/test/resources/features/
5. **Фикстуры** — синхронизация: `sync_features.py sync <source> <module>` (единый каталог `src/test/resources/features/`)
6. **Запуск тестов** — команда запуска (`mvn clean test`), профили

**Формат каждой задачи:**
```markdown
- [ ] X.Y <Описание>
  — Файл: <путь к создаваемому/изменяемому файлу>
  — Связь: <ID фраз / feature-файл / мок>
  — Зависит от: X.Z
```

**Для change-mode:** задачи в tasks.md фокусируются на delta:
- Новые step definitions только для delta-фраз
- Новые моки (если есть)
- Перенос delta features и fixtures (не всех, только новых)
- Интеграционные тесты только для новых сценариев

**Правила:**
- Порядок: по зависимостям (инфраструктура → моки → шаги → feature → запуск тестов)
- Размер: каждая задача выполнима за одну сессию
- Каждая задача содержит конкретный файл для создания/изменения
- Конкретные имена классов и файлов — из выводов шага 3a

**Группировка задач (MUST):** задачи в tasks.md группируются по классам артефактов (моки, step definitions, фикстуры). Один edit — для всего класса (например, один метод в SharedHttp_Steps для всех W-фраз, затем один compile-gate). Запрещено создавать отдельную задачу на каждую фразу/мок — это создаёт десятки мелких edit+compile циклов.

**Пример группировки задач в tasks.md:**
```markdown
## 1. Подготовка
- [ ] 1.1 ...

## 2. Мокирование
- [ ] 2.1 Создать все MockServer-классы (одна задача, внутри — список моков)
- [ ] 2.2 Настроить application-test.yml test.mocks
## 3. Step definitions
```

## Guardrails

- **Всегда** читай `test.md` перед началом
- **Всегда** опирайся на артефакты `opentest-new-test` (spec-режим)
- **НЕ читай** код реализации (`.java`, `.py`, `.kt`, `.go`, `.ts`)
- **Можно читать** только файлы контрактов (OpenAPI, JSON Schema, Avro, Protobuf, DDL/Liquibase) по путям из `.research/test-architecture-as-is.yaml` или `features/*.feature` (если доступно) и тестовую инфраструктуру (step definitions, конфиги) через субагент на шаге 2.5
- **Инфраструктурные сервисы (PostgreSQL, Kafka) НЕ поднимаются и НЕ мокаются фреймворком.** Мокаются только бизнес-зависимости (distr, ctrl, stash и т.п. — любые сервисы, с которыми тестируемый сервис общается по HTTP/gRPC) через MockWebServer. Инфраструктура (БД, очереди) — зона ответственности пользователя
- **НЕ пиши запретительных фраз** («Docker ЗАПРЕЩЁН», «запрещено использовать...») — если везде указан Podman, этого достаточно.
- **НЕ пиши списков действий пользователя** («Пользователь должен: 1... 2...»). Ограничься формулой «Инфраструктурные сервисы — зона ответственности пользователя. Контейнеры должны быть запущены до запуска тестов.»
- **НЕ придумывай** технологии/библиотеки, не упомянутые в `test-architecture-as-is.md` или референсной архитектуре
- Если контекст неясен — задавай вопросы, не делай предположений
- `design.md` должен ссылаться на конкретные сущности из контрактов
- `tasks.md` должен быть реализуемым — не добавляй нереальные задачи
- **В tasks.md НЕ создавать задачи:** DDL-скрипты, podman-compose для БД, ContainerManager с авто-DDL, CREATE TABLE в step definitions. Инфраструктура (БД, Kafka) предоставляется пользователем.
- При обновлении файлов сохраняй уже заполненные данные, если они корректны
- **Данные создаются через API.** Способ подготовки фикстур по умолчанию — API-seed (GC-004/GC-005). Прямой INSERT — только для справочников и исключений, одобренных через Gate: DB Write Approval.
- **SELECT для верификации — всегда разрешён.** TC-005, TC-006, TC-007 — только чтение из БД. INSERT/UPDATE/DELETE данных — только с согласованием.
- **DELETE FROM для изоляции — всегда разрешён.** Очистка таблиц между сценариями — не бизнес-операция.
- **Команды `projects_yaml.py` запускай из корня тестового проекта** (cwd = каталог, содержащий `opentest/`). Каталог навыка (`$SKILLS_DIR/opentest-design/`) — это не корень проекта. Не передавай его в `directory`/`workdir` инструмента `run_shell_command`/`bash` — скрипт завершится с exit 3 (self-defending guard)

### Правила для Phrases-First подхода

- **Фразы НЕ изменяются в design.** Они спроектированы в new-test (Phrases-First). Если обнаружен пробел — зафиксируй в design.md §5.2 как «пробел new-test» и сообщи пользователю.
- **API-seed фразы (GC-004/GC-005/GC-006) приоритетнее DB-seed (GC-007).** Если данные можно создать через API — используй API. DB-seed — только если одобрено на шаге 4 cross-check D.
- **DB-seed фразы должны иметь Gate: DB Write Approval.** Без комментария о согласовании в phrases.yml — пауза, запроси подтверждение (шаг 4 cross-check D).
- **Logbook ДОЛЖЕН быть включён** для всех HTTP-взаимодействий тестов с сервисом. Без него отладка вслепую.
- **Custom Type Registry ДОЛЖЕН быть создан** с типами `{val}` и `{path}`. Reference архитектура уже включает их.
- **SQL-касты `::integer` и `::bigint` НЕ ИСПОЛЬЗУЮТСЯ** — JDBC их игнорирует. Используй Java-side setObject с правильным типом.
- **TRUNCATE vs DELETE** — по умолчанию DELETE FROM (безопаснее, не требует cascade прав). TRUNCATE только если пользователь явно подтвердил права.

### Правила для canonical phrases и generator

- **Расширенный canonical-реестр.** Текущие canonical-фразы покрывают типовые паттерны: Kafka asserts (TC-008 positive, TC-009 negative), DB-check с переменной (TC-010) и negative DB-check (TC-011), установка header (WC-004) и пропуск header (WC-005), composite setup через явные цепочки (GC-004 → WC-001 → GC-005). Точные диапазоны и количество — через `python3 $SKILLS_DIR/opentest-phrases/scripts/phrases.py count` / `ranges` (не хардкодить). Если шаг в `features/*.feature` матчится на canonical-фразу — design ссылается на её ID в §2.3 без создания delta. Delta (G/W/T-префиксы) — только для сервисо-специфичных фраз, не покрытых canonical.
- **§2.3 design.md НЕ пишется агентом.** Только скриптом `generate-phrase-mapping.py` (шаг 8). Ручная правка между маркерами `<!-- BEGIN AUTO: phrase-mapping -->` будет перезаписана.
- **§2.2.1 design.md — единственное место для delta-фраз.** Формат YAML между маркерами `<!-- BEGIN AUTO: delta-phrases -->` ... `<!-- END AUTO: delta-phrases -->`. См. документация скрипта.
- **State-declaration contract (MUST):** каждая delta-фраза в YAML-блоке §2.2.1 ДОЛЖНА содержать поля `state_writes` и/или `state_reads` (или явно пустые). Если поле отсутствует — генератор `generate-phrase-mapping.py` обязан выдать ERROR «delta-фраза <ID> без state-declaration» и завершиться с exit 1.
- **Delta ID монотонны: G-001+, W-001+, T-001+.** Canonical ID (<!-- BEGIN AUTO: phrases:ranges -->GC-001..GC-007, WC-001..WC-005, TC-001..TC-011<!-- END AUTO: phrases:ranges -->) и delta ID (G/W/T) — независимые пространства, коллизия невозможна.
- **Если canonical-фраза не реализована в reference — это баг reference.** Сообщи пользователю (Stop-and-Report), НЕ добавляй её в delta. Генератор выдаст ERROR «canonical ID X не реализована в reference» — это блокирующая ошибка.
- **Canonical = immutable contract.** Удаление или переопределение canonical ID — breaking change, требует явной санкции пользователя и patch reference-архитектуры + smoke-feature.

## Reference architecture = canonical implementation

- Reference реализует **ВСЕ** canonical фразы. Это гарантия контракта.
- **Patch canonical** → обязательный patch reference + расширение smoke-feature. Три шага неразделимы.
- **Extra-шаги** (не-canonical step definitions) — **запрещены**. Reference не должен содержать шагов сверх canonical.
- Если canonical-фраза не реализована в reference — это баг reference, требующий GAP-закрытия (добавить метод + smoke-сценарий).

## Когда применять

- Стек сервиса: Java 21+, Spring Boot 3.x, Maven
- BDD-раннер: Cucumber-JVM + JUnit Platform Suite
- Мокирование: OkHttp MockWebServer (для HTTP-зависимостей)
- HTTP-логирование: Logbook (по умолчанию включено)
- Контейнеризация: Podman (только для образа тестируемого сервиса). Инфраструктура (PostgreSQL, Kafka) предоставляется пользователем
- База данных: PostgreSQL (через JdbcTemplate для проверок)
- HTTP-клиент в тестах: Spring WebClient
- Assertions: AssertJ + JsonUnit (schema-driven JSON/DB-сравнения)
- Custom Cucumber Types: `{val}`, `{path}` — для значений с кавычками/без и dot-путей

## Как адаптировать под свой проект

**Весь проектно-специфичный код — в `application-test.yml`.** Java-файлы не нужно редактировать.

### 1. Заполнить `application-test.yml`

```yaml
test:
  service:                          # Тестируемый сервис
    image: <your-image>:latest
    port: <service-port>
    env:
      <YOUR_SERVICE_URL>: http://localhost:<mock-port>
      ...

  mocks:                            # Мок-сервисы (имя → порт)
    <mock-name-1>:
      port: <port-1>
    <mock-name-2>:
      port: <port-2>

  db:                               # БД конфигурация
    clean-tables:                   # Таблицы для DELETE FROM перед каждым сценарием. Набор — из interview-decisions.yaml → cleanup_tables (DB-check фразы ∪ seed side-effects)
      - table_one
      - table_two
    column-types:                   # Маппинг типов для JDBC (не-text колонки)
      - column: table_name.column_name
        type: bigint
      - column: table_name.other_column
        type: jsonb

  multipart-endpoints:              # Эндпоинты с multipart/form-data
    - /api/v1/upload
```

Также обновить плейсхолдеры:
- `<database>` → имя БД
- `<schema>` → имя схемы
- DB credentials (username/password)

### 2. Обновить `pom.xml`

Заменить плейсхолдеры `<service>`, `<database>`, `<schema>`, `com.example`.

### 3. Feature-файлы и фикстуры

Перенести `.feature` файлы в `src/test/resources/features/`, фикстуры — в `src/test/resources/features/` (вместе с `.feature` файлами).

### `fixture:` маркер

Все ссылки на фикстуры в .feature файлах используют префикс `fixture:`:

- **Относительный путь:** `fixture:<role>/<filename>` (путь относительно каталога фикстур текущей фичи)
  - Например: `"fixture:request/create-release.json"` → `/features/<feature-name>/request/create-release.json`
  - Имя текущей фичи добавляется автоматически через `@Before` hook (см. `CucumberSpringConfiguration.java`)

`FixtureResolver.java` выполняет резолвинг. Все `getResourceAsStream` вызовы проходят через `FixtureResolver.resolve()`.

> **Абсолютный путь `fixture:/<path>` для JSON-фикстур запрещён (FX13)** в feature-файлах проектов. Фикстуры строго локальны в каталоге-потребителе (`features/<feature-name>/`).
>
> **Исключение — canonical smoke-feature.** Файл `all-canonical-phrases.feature` с тегом `@canonical-smoke` сохраняет доступ к общим smoke-фикстурам из `features/all-canonical/` через `fixture:/<path>`. Поддержка абсолютного пути в `FixtureResolver.java` остаётся для smoke exempt и обратной совместимости. Валидатор FX13 определяет exempt по наличию тега `@canonical-smoke` на Feature.

## Schema Assertions: формат фикстур

> **Для БД-сценариев (TC-005/TC-006/TC-007) SQL-касты для non-text колонок обязательны** — см. матрицу совместимости в `application-test.yml` (комментарий-контракт в секции БД). `assertQueryMatches` использует `queryForObject(String.class)` — JDBC возвращает String, и PG-native типы (boolean, array, jsonb) требуют SQL-кастов для корректного JSON-сравнения.

Фикстуры для schema-сравнения хранятся в `src/test/resources/features/<feature-name>/expected/`. Формат:

```json
{
  "$options": {"ignoreExtraFields": true, "ignoreArrayOrder": true, "tolerance": 0.01},
  "field1": "exact-value",
  "field2": "${json-unit.any-string}",
  "field3": "${json-unit.any-number}",
  "field4": "${json-unit.any-boolean}",
  "field5": "${savedVariable}"
}
```

**Директивы:**

| Директива | Описание |
|-----------|----------|
| `$options` | Управление сравнением: `ignoreExtraFields`, `ignoreArrayOrder`, `tolerance` |
| `$data` | Обёртка для ожидаемых массивов (корень = `$options`, данные = `$data`) |
| `${json-unit.any-string}` | Плейсхолдер: любое строковое значение |
| `${json-unit.any-number}` | Плейсхолдер: любое число |
| `${json-unit.any-boolean}` | Плейсхолдер: любой boolean |
| `${varName}` | Переменная из TestContext (резолвится перед сравнением) |

**Пример — массив с `$data`:**
```json
{
  "$options": {"ignoreArrayOrder": true, "ignoreExtraFields": true},
  "$data": [
    {"id": "${json-unit.any-number}", "name": "${json-unit.any-string}"}
  ]
}
```

**Пример — SQL-запрос для `queryResultMatchesSchema`:**

Файл `features/<feature-name>/queries/my-query.sql`:
```sql
SELECT row_to_json(t) FROM my_table t WHERE id = ${recordId}
```

Переменные `${varName}` в SQL резолвятся из TestContext перед выполнением.

package com.example.test;

import java.io.BufferedReader;
import java.io.BufferedWriter;
import java.io.File;
import java.io.FileWriter;
import java.io.IOException;
import java.io.InputStreamReader;
import java.net.HttpURLConnection;
import java.net.URL;
import java.nio.file.Files;
import java.nio.file.StandardOpenOption;
import java.time.Duration;
import java.time.LocalDate;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.TimeUnit;

import com.github.dockerjava.api.model.HostConfig;
import com.github.dockerjava.api.model.LogConfig;
import com.github.dockerjava.api.model.LogConfig.LoggingType;
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import org.testcontainers.containers.GenericContainer;
import org.testcontainers.utility.DockerImageName;

/**
 * Управляет ТОЛЬКО образом тестируемого сервиса через Podman.
 * Инфраструктурные сервисы (PostgreSQL, Kafka и др.) предоставляются пользователем и не управляются этим классом.
 */
@Component
@Slf4j
public class ContainerManager {

    private final TestConfigProperties config;
    private GenericContainer<?> container;
    private final List<Process> logProcesses = new CopyOnWriteArrayList<>();

    public ContainerManager(TestConfigProperties config) {
        this.config = config;
    }

    @PostConstruct
    public void start() {
        var simConfig = config.service();
        if (!simConfig.enabled()) {
            log.info("Container disabled via test.service.enabled=false — assuming service is already running");
            return;
        }
        var logConfig = config.logging();

        var c = new GenericContainer<>(
                DockerImageName.parse(simConfig.image()))
                .withImagePullPolicy(imageName -> false)
                .withStartupTimeout(Duration.ofSeconds(simConfig.startupTimeoutSeconds()))
                .withCreateContainerCmdModifier(cmd -> {
                    HostConfig hc = cmd.getHostConfig();
                    if (hc != null) {
                        hc.withNetworkMode("host");
                        hc.withLogConfig(new LogConfig(LoggingType.JSON_FILE, Collections.emptyMap()));
                    }
                });
        simConfig.env().forEach(c::withEnv);
        container = c;

        startLogCapture(logConfig);
        container.start();
        waitForHealth(simConfig.port(), simConfig.startupTimeoutSeconds(), simConfig.healthPath(),
                simConfig.healthConnectTimeoutMs(), simConfig.healthRetryIntervalMs());
    }

    @PreDestroy
    public void stop() {
        stopAllLogProcesses();
        if (container != null) {
            container.stop();
        }
    }

    private void startLogCapture(TestConfigProperties.Logging logConfig) {
        Thread waiter = new Thread(() -> {
            String containerId = null;
            while (containerId == null) {
                containerId = container.getContainerId();
                if (containerId == null) {
                    try {
                        Thread.sleep(100);
                    } catch (InterruptedException e) {
                        return;
                    }
                }
            }
            File dir = new File(logConfig.dir());
            dir.mkdirs();
            cleanOldLogs(dir, "service", logConfig.retentionDays());
            String logFile = "service-" + LocalDate.now() + ".log";
            File file = new File(dir, logFile);
            try {
                BufferedWriter writer = new BufferedWriter(new FileWriter(file, true));
                Process process = new ProcessBuilder(
                        "podman", "logs", "-f", containerId
                ).redirectErrorStream(true).start();
                logProcesses.add(process);
                Thread reader = new Thread(() -> {
                    try (BufferedReader br = new BufferedReader(new InputStreamReader(process.getInputStream()))) {
                        String line;
                        while ((line = br.readLine()) != null) {
                            writer.write(line);
                            writer.newLine();
                            writer.flush();
                        }
                    } catch (IOException e) {
                        // stream closed or process destroyed
                    } finally {
                        try {
                            writer.close();
                        } catch (IOException ignored) {
                        }
                    }
                }, "podman-logs-service");
                reader.setDaemon(true);
                reader.start();
            } catch (IOException e) {
                log.error("Failed to start podman log follow", e);
            }
        }, "log-waiter-service");
        waiter.setDaemon(true);
        waiter.start();
    }

    private void cleanOldLogs(File dir, String containerName, int retentionDays) {
        LocalDate cutoff = LocalDate.now().minusDays(retentionDays);
        File[] files = dir.listFiles((d, name) ->
                name.startsWith(containerName + "-") && name.endsWith(".log"));
        if (files != null) {
            for (File f : files) {
                String name = f.getName();
                String dateStr = name.substring(containerName.length() + 1, name.length() - 4);
                try {
                    if (LocalDate.parse(dateStr).isBefore(cutoff)) {
                        f.delete();
                    }
                } catch (Exception ignored) {
                }
            }
        }
    }

    private void waitForHealth(int port, int timeoutSeconds, String healthPath,
                               int connectTimeoutMs, int retryIntervalMs) {
        for (int i = 0; i < timeoutSeconds; i++) {
            try {
                URL url = new URL("http://localhost:" + port + healthPath);
                HttpURLConnection c = (HttpURLConnection) url.openConnection();
                c.setConnectTimeout(connectTimeoutMs);
                c.setReadTimeout(connectTimeoutMs);
                if (c.getResponseCode() == 200) {
                    log.info("Health check passed on port {}", port);
                    return;
                }
            } catch (Exception ignored) {
            }
            try {
                Thread.sleep(retryIntervalMs);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                break;
            }
        }
        throw new RuntimeException("Health check failed after " + timeoutSeconds + "s");
    }

    private void stopAllLogProcesses() {
        for (Process p : logProcesses) {
            p.destroy();
        }
        for (Process p : logProcesses) {
            try {
                p.waitFor(5, TimeUnit.SECONDS);
            } catch (InterruptedException ignored) {
            }
            if (p.isAlive()) {
                p.destroyForcibly();
            }
        }
        logProcesses.clear();
    }

package com.example.test;

/**
 * Резолвит fixture: ссылки в classpath-пути.
 *
 * Относительный путь:  fixture:request/file.json
 *   → /features/<currentFeatureName>/request/file.json
 *
 * Абсолютный путь:     fixture:/all-canonical/file.json
 *   → /features/all-canonical/file.json
 */
public final class FixtureResolver {

    private static final String FIXTURE_PREFIX = "fixture:";

    private FixtureResolver() {}

    public static String resolve(String ref) {
        if (ref == null || !ref.startsWith(FIXTURE_PREFIX)) {
            throw new IllegalArgumentException(
                "Fixture reference must start with 'fixture:': " + ref);
        }
        String path = ref.substring(FIXTURE_PREFIX.length());
        if (path.startsWith("/")) {
            return "/features" + normalize(path);
        }
        String featureName = TestContext.getCurrentFeatureName();
        if (featureName == null) {
            throw new IllegalStateException(
                "Feature name not set — @Before hook did not run. " +
                "Ensure CucumberSpringConfiguration.trackCurrentFeature is registered.");
        }
        return "/features/" + featureName + "/" + normalize(path);
    }

    private static String normalize(String path) {
        if (path == null || path.isEmpty()) {
            throw new IllegalArgumentException("fixture: path is empty");
        }
        if (path.contains("..")) {
            throw new IllegalArgumentException("fixture: path traversal not allowed: " + path);
        }
        return path.replace("//", "/");
    }
}

    }

package com.example.test;

import java.util.List;
import java.util.Map;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

/**
 * Резолв ${varName}-плейсхолдеров из {@link TestContext}.
 *
 * <p>Два режима:
 * <ul>
 *   <li>{@link #resolve(String)} — lenient: неразрешённые ${var} остаются как есть.
 *       Используется для schema/sql-фикстур (TC-004..TC-007), где ${json-unit.*} и
 *       неизвестные переменные допустимы.</li>
 *   <li>{@link #resolveStrict(String, String)} — strict: неразрешённая переменная (кроме
 *       ${json-unit.*}) → {@link IllegalStateException} с указанием фикстуры и имени.
 *       Используется для request-body фикстур (WC-002, GC-004), где буквальная
 *       отправка ${var} — всегда баг сценария.</li>
 * </ul>
 *
 * <p>Чистая string-замена по regex {@code \$\{([^}]+)\}}. Тип переменной не сохраняется —
 * Integer/Boolean из ответа конвертируются в String при сохранении (см. SharedData_Steps
 * GC-005: {@code node.asText()}). Поэтому форма плейсхолдера в request-фикстуре определяется
 * типом поля (schema.type), НЕ значением переменной: numeric/boolean → незакавыченная
 * {@code ${var}} (после подстановки {@code "42"} → {@code 42} на wire, тип-корректно без
 * coercion); string → закавыченная {@code "${var}"}. Закавыченная форма для numeric/boolean
 * ({@code "${var}"}) остаётся JSON-строкой после резолва и работает только через Jackson
 * coercion сервиса (которая может быть отключена) — не полагаться на неё.
 */
public final class VariableResolver {

    private static final Pattern VAR = Pattern.compile("\\$\\{([^}]+)}");
    private static final Pattern FIELD_SEGMENT = Pattern.compile(
        "^([a-zA-Z_][a-zA-Z0-9_-]*)((?:\\[\\d+\\])*)$");
    private static final Pattern ARRAY_INDEX = Pattern.compile("\\[(\\d+)]");

    private VariableResolver() {}

    /**
     * Разрешает path-выражение (без обрамляющих {@code ${ }}), например
     * {@code response.body.id} или {@code response.body.items[0].name},
     * навигируя по nested Map/List структуре из {@link TestContext#getVariables()}.
     *
     * @param pathExpr путь без {@code ${ }} (nullable)
     * @return строковое значение (через {@link #objectToString}), либо {@code null}
     */
    public static String resolveValue(String pathExpr) {
        if (pathExpr == null) return null;
        return objectToString(navigatePath(pathExpr));
    }

    private static Object navigatePath(String expr) {
        String[] segments = expr.split("\\.");
        Object current = TestContext.getVariables().get(segments[0]);
        if (current == null) return null;
        for (int i = 1; i < segments.length; i++) {
            current = navigateSegment(current, segments[i]);
            if (current == null) return null;
        }
        return current;
    }

    private static Object navigateSegment(Object current, String segment) {
        Matcher m = FIELD_SEGMENT.matcher(segment);
        if (!m.matches()) return null;
        String fieldName = m.group(1);
        String indices = m.group(2);
        if (current instanceof Map<?, ?> map) {
            current = map.get(fieldName);
        } else {
            return null;
        }
        if (current != null && indices != null && !indices.isEmpty()) {
            Matcher idxMatcher = ARRAY_INDEX.matcher(indices);
            while (idxMatcher.find() && current != null) {
                int idx = Integer.parseInt(idxMatcher.group(1));
                if (current instanceof List<?> list && idx < list.size()) {
                    current = list.get(idx);
                } else {
                    return null;
                }
            }
        }
        return current;
    }

    private static String objectToString(Object obj) {
        if (obj == null) return null;
        if (obj instanceof String) return (String) obj;
        return obj.toString();
    }

    /**
     * Lenient resolution: неразрешённые ${var} (кроме ${json-unit.*}) остаются как есть.
     *
     * @param content контент с плейсхолдерами (nullable)
     * @return контент с подставленными значениями (null если input null)
     */
    public static String resolve(String content) {
        if (content == null) return null;
        Matcher matcher = VAR.matcher(content);
        StringBuilder sb = new StringBuilder();
        while (matcher.find()) {
            String varName = matcher.group(1);
            if (varName.startsWith("json-unit.")) {
                matcher.appendReplacement(sb, Matcher.quoteReplacement(matcher.group(0)));
                continue;
            }
            String value;
            if (varName.contains(".") || varName.contains("[")) {
                value = objectToString(navigatePath(varName));
            } else {
                value = TestContext.getVariable(varName);
            }
            if (value != null) {
                matcher.appendReplacement(sb, Matcher.quoteReplacement(value));
            } else {
                matcher.appendReplacement(sb, Matcher.quoteReplacement(matcher.group(0)));
            }
        }
        matcher.appendTail(sb);
        return sb.toString();
    }

    /**
     * Strict resolution: неразрешённая переменная (кроме ${json-unit.*}) → throw.
     *
     * @param content     контент с плейсхолдерами (nullable)
     * @param fixtureName имя фикстуры (для диагностического сообщения)
     * @return контент с подставленными значениями (null если input null)
     * @throws IllegalStateException если переменная не найдена в TestContext
     */
    public static String resolveStrict(String content, String fixtureName) {
        if (content == null) return null;
        Matcher matcher = VAR.matcher(content);
        StringBuilder sb = new StringBuilder();
        while (matcher.find()) {
            String varName = matcher.group(1);
            if (varName.startsWith("json-unit.")) {
                matcher.appendReplacement(sb, Matcher.quoteReplacement(matcher.group(0)));
                continue;
            }
            String value;
            if (varName.contains(".") || varName.contains("[")) {
                value = objectToString(navigatePath(varName));
            } else {
                value = TestContext.getVariable(varName);
            }
            if (value != null) {
                matcher.appendReplacement(sb, Matcher.quoteReplacement(value));
            } else {
                throw new IllegalStateException(
                    "Неразрешённая переменная ${" + varName + "} в фикстуре '" +
                    fixtureName + "'. Сохраните её ранее в сценарии через " +
                    "«И клиент сохранил response.<field> как переменную \"" + varName + "\"»."
                );
            }
        }
        matcher.appendTail(sb);
        return sb.toString();
    }

                    mpBuilder.part(entry.getKey(), entry.getValue().content())
                            .filename(entry.getValue().fileName());
                }

            uriSpec.body(BodyInserters.fromMultipartData(mpBuilder.build()));
        } else if (body != null && !body.isEmpty()) {
            body = VariableResolver.resolveStrict(body, requestFixtureName.get());
            uriSpec = uriSpec.contentType(MediaType.APPLICATION_JSON);
            uriSpec.bodyValue(body);
        }

        try {
            var result = uriSpec
                    .retrieve()
                    .toEntity(String.class)
                    .block(Duration.ofSeconds(30));
            if (result != null) {
                com.example.test.TestContext.setResponseStatus(result.getStatusCode().value());
                com.example.test.TestContext.setResponseBody(result.getBody());
                com.example.test.TestContext.populateResponse(

            }
            com.example.test.TestContext.populateRequest(method, resolvedPath, body);
        } catch (WebClientResponseException e) {
            com.example.test.TestContext.setResponseStatus(e.getStatusCode().value());
            com.example.test.TestContext.setResponseBody(e.getResponseBodyAsString());
            com.example.test.TestContext.populateResponse(

            com.example.test.TestContext.populateRequest(method, resolvedPath, body);

            requestFixtureName.remove();
            attachedFiles.remove();
            com.example.test.TestContext.getRequestHeaders().clear();
            com.example.test.TestContext.getAbsentHeaders().clear();
        }
    }

/**

 *
 * <p>Использует {@link KafkaRecordsManager} как in-memory кэш сообщений.
 * В реальных проектах кэш наполняется Kafka consumer'ом; в reference-архитектуре

@Slf4j

public class SharedKafka_Steps {

    private static KafkaRecordsManager kafkaRecordsManager;
    private static ObjectMapper objectMapper;

    @Autowired
    public void init(KafkaRecordsManager manager, ObjectMapper mapper) {
        if (kafkaRecordsManager == null) {
            kafkaRecordsManager = manager;
            objectMapper = mapper;
        }
    }

    /**
     * Сброс Kafka-кэша перед каждым сценарием + smoke-seed для reference-архитектуры.
     *
     * <p>Smoke-seed — это <b>внутренний механизм reference</b>: реальный проект

     * consumer'а. Это НЕ canonical-фраза.
     */
    @Before(order = 40)
    public void resetKafkaRecords() {
        kafkaRecordsManager.clear();
        seedSmokeTopics();
    }

    private void seedSmokeTopics() {
        seedFromResource("release-events", "fixture:/all-canonical/t013-kafka-seed.json");
    }

    private void seedFromResource(String topic, String fixturePath) {
        var resource = getClass().getResourceAsStream(FixtureResolver.resolve(fixturePath));
        if (resource == null) {
            log.warn(">>> Kafka smoke-seed fixture not found: features/{}", fixturePath);
            return;
        }
        try {
            JsonNode payload = objectMapper.readTree(resource);
            kafkaRecordsManager.record(topic, payload);
            log.info(">>> Kafka smoke-seed: topic='{}' payload={}", topic, payload);
        } catch (IOException e) {
            log.warn(">>> Failed to read Kafka smoke-seed fixture {}: {}", fixturePath, e.getMessage());
        }
    }

    // --- TC-008 ---

    @Тогда("в Kafka-топике \"{word}\" опубликовано сообщение, соответствующее схеме \"{val}\"")
    public void kafkaMessageMatchesSchema(String topic, String fixture) {
        log.info(">>> Тогда в Kafka-топике \"{}\" опубликовано сообщение, соответствующее схеме \"{}\"", topic, fixture);
        List<JsonNode> records = kafkaRecordsManager.getRecords(topic);
        assertThat(records)
                .as("В Kafka-топике '%s' нет ни одного сообщения", topic)
                .isNotEmpty();
        JsonNode last = records.get(records.size() - 1);
        String actualJson = last.toString();
        SchemaAssertion.assertMatches(actualJson, fixture);
    }

    // --- TC-009 ---

    @Тогда("в Kafka-топике \"{word}\" НЕ опубликовано сообщение с полем \"{word}\" равным \"{val}\"")
    public void kafkaNoMessageWithField(String topic, String field, String value) {
        log.info(">>> Тогда в Kafka-топике \"{}\" НЕ опубликовано сообщение с полем \"{}\" равным \"{}\"",
                topic, field, value);
        List<JsonNode> records = kafkaRecordsManager.getRecords(topic);
        for (JsonNode msg : records) {
            JsonNode fieldNode = msg.path(field);
            if (!fieldNode.isMissingNode() && !fieldNode.isNull() && value.equals(fieldNode.asText())) {
                throw new AssertionError(
                        "Ожидалось отсутствие сообщения в топике '" + topic + "' с полем '"
                                + field + "' равным '" + value + "', но найдено: " + msg);
            }
        }
        // Пустой топик или нет matching-сообщений — assertion проходит.
    }
}

# Guardrails — ограничения для opentest-design

> **Единственный источник правды:** секция **Guardrails** в `SKILL.md`.
> Этот файл содержит только дополнения и пояснения, не дублирующие SKILL.md.

---

## Дополнения к Guardrails из SKILL.md

### Чтение исходного кода реализации — ЗАПРЕЩЕНО

Файлы `.java`, `.py`, `.kt`, `.go`, `.ts`, `.js`, `.cs` и другие production-файлы.
Контроллеры, репозитории, сервисы — **НИКАКОГО production-кода**.

### Фикстуры — IMMUTABLE

Файлы в `fixtures/` созданы `opentest-new-test` и валидированы через Gate 2.
Design НЕ создаёт, НЕ изменяет и НЕ удаляет их.
Если фикстура отсутствует или некорректна — это баг new-test.

### Проектирование вслепую — ЗАПРЕЩЕНО

Всегда опирайся на артефакты `opentest-new-test`. Если данных не хватает — спроси пользователя.

### Принципы

- **Опирайся на артефакты `opentest-new-test`** — они единственный источник правды
- **Не читай код реализации** — ни при каких обстоятельствах
- **Если неясно — спроси пользователя** — не додумывай
- **ДОЛЖЕН / СЛЕДУЕТ / МОЖЕТ** — используй уровни обязательности
- **API-first для предусловий**: данные создаются через API. Прямой SQL (GC-007 — INSERT/UPDATE/DELETE/ALTER SEQUENCE) — только если одобрен пользователем (Gate: DB Write Approval). SELECT для верификации — всегда разрешён. DELETE FROM для изоляции — всегда разрешён.
- **Seed бизнес-сущностей — через GC-004 в Gherkin** (видимость для читателя теста); cleanup таблиц — через `@Before` hook (не Gherkin), список из `interview-decisions.yaml` → `cleanup_tables`. JSON-фикстуры строго локальны в каталоге-потребителе; `fixture:/<path>` для JSON запрещён (FX13). Исключение — canonical smoke-feature с тегом `@canonical-smoke`.
- **Фразы НЕ изменяются в design.** Они спроектированы в new-test. Пробел → баг new-test.

#!/usr/bin/env python3
"""Generate §2.3 phrase-mapping table for design.md.

Validates that all canonical phrases (from opentest-phrases/phrases.yml)
are implemented in the reference-architecture Java step definitions, parses delta
phrases from design.md §2.2.1 (YAML block), and generates the machine-readable
mapping table in §2.3.

Uses PyYAML (yaml.safe_load) for canonical phrases.yml. Exit 0 = OK, exit 1 = validation errors.

Usage:
    python3 generate-phrase-mapping.py \\
        --design <path/to/design.md> \\
        [--canonical <path/to/opentest-phrases/phrases.yml>] \\
        --reference <path/to/opentest-design/reference-architectures/java-cucumber-spring> \\
        [--in-place]

    --canonical по умолчанию: ../opentest-phrases/phrases.yml (от каталога навыка).
"""

from __future__ import annotations

import argparse
import re
import sys
from dataclasses import dataclass, field
from pathlib import Path
from typing import Dict, List, Optional

import yaml


# Канонический реестр фраз (SSot) — по умолчанию для --canonical.
DEFAULT_CANONICAL = Path(__file__).resolve().parent.parent.parent / "opentest-phrases" / "phrases.yml"


# ============================================================
# Canonical phrases.yml parsing
# ============================================================

PHRASE_MARKER_BEGIN = "<!-- BEGIN AUTO: phrase-mapping -->"
PHRASE_MARKER_END = "<!-- END AUTO: phrase-mapping -->"
DELTA_MARKER_BEGIN = "<!-- BEGIN AUTO: delta-phrases -->"
DELTA_MARKER_END = "<!-- END AUTO: delta-phrases -->"


@dataclass
class CanonicalPhrase:
    id: str
    text: str
    params: str
    category: str  # G | W | T


def parse_canonical(path: Path) -> List[CanonicalPhrase]:
    """Parse canonical phrases.yml → list of CanonicalPhrase."""
    data = yaml.safe_load(path.read_text(encoding="utf-8"))
    if not isinstance(data, dict) or "phrases" not in data:
        return []
    phrases: List[CanonicalPhrase] = []
    seen_ids = set()
    for entry in data["phrases"]:
        if not isinstance(entry, dict):
            continue
        phrase_id = entry.get("id", "")
        if not phrase_id or phrase_id in seen_ids:
            continue
        seen_ids.add(phrase_id)
        category = phrase_id[0]
        phrases.append(CanonicalPhrase(
            id=phrase_id,
            text=entry.get("text", ""),
            params=entry.get("params", ""),
            category=category,
        ))
    return phrases


# ============================================================
# Reference Java step definitions parsing
# ============================================================

ANNOTATION_RE = re.compile(
    r"""^\s*@(Дано|Когда|Тогда|И)\s*\(\s*"(.*?)"\s*\)\s*$"""
)
METHOD_RE = re.compile(r"^\s*public\s+(?:static\s+)?\S+\s+(\w+)\s*\(")


@dataclass
class JavaStep:
    annotation_kind: str  # Дано | Когда | Тогда | И
    raw_text: str  # exactly as in Java string literal
    class_name: str
    method_name: str


def parse_reference(reference_root: Path) -> List[JavaStep]:
    """Parse all Shared*_Steps.java files → list of JavaStep."""
    steps: List[JavaStep] = []
    steps_dir = reference_root / "module" / "src" / "test" / "java" / "com" / "example" / "test" / "steps"
    if not steps_dir.is_dir():
        # fallback: glob anywhere under reference_root
        steps_files = list(reference_root.rglob("Shared*_Steps.java"))
    else:
        steps_files = sorted(steps_dir.glob("Shared*_Steps.java"))
    for java_file in steps_files:
        class_name = java_file.stem
        pending_annotation: Optional[tuple[str, str]] = None
        for line in java_file.read_text(encoding="utf-8").splitlines():
            if pending_annotation is None:
                m = ANNOTATION_RE.match(line)
                if m:
                    kind, raw = m.group(1), m.group(2)
                    # allow same-line method or next-line method
                    pending_annotation = (kind, raw)
                    continue
            else:
                m_method = METHOD_RE.match(line)
                if m_method:
                    kind, raw = pending_annotation
                    steps.append(
                        JavaStep(
                            annotation_kind=kind,
                            raw_text=raw,
                            class_name=class_name,
                            method_name=m_method.group(1),
                        )
                    )
                    pending_annotation = None
    return steps


# ============================================================
# Normalization & matching
# ============================================================

PLACEHOLDER_RE = re.compile(r"\{[^}]+\}")
ANGLE_PLACEHOLDER_RE = re.compile(r"<[^>]+>")
ESCAPE_RE = re.compile(r'\\(["\'])')
WHITESPACE_RE = re.compile(r"\s+")


def normalize_phrase(text: str) -> str:
    """Normalize phrase text for structural matching.

    Handles two representation formats:
    - Canonical phrases.yml: documentation placeholders like ``<table>``, ``<field>``
    - Reference Java annotations: Cucumber Expressions like ``{word}``, ``{val}``

    Both are replaced with ``{*}`` for structural comparison.
    Also unescapes Java string escapes and removes quotes around placeholders
    (canonical uses quotes for readability, reference uses {string} which matches quoted values).
    """
    text = ESCAPE_RE.sub(r"\1", text)
    text = PLACEHOLDER_RE.sub("{*}", text)
    text = ANGLE_PLACEHOLDER_RE.sub("{*}", text)
    text = text.replace('"{*}"', "{*}")
    text = WHITESPACE_RE.sub(" ", text).strip()
    return text


def build_reference_index(steps: List[JavaStep]) -> Dict[str, JavaStep]:
    """Map normalized annotation text → JavaStep."""
    index: Dict[str, JavaStep] = {}
    for s in steps:
        key = normalize_phrase(s.raw_text)
        if key not in index:
            index[key] = s
    return index


def match_canonical_to_reference(
    canonical: List[CanonicalPhrase], ref_index: Dict[str, JavaStep]
) -> tuple[List[tuple[CanonicalPhrase, JavaStep]], List[CanonicalPhrase]]:
    matched: List[tuple[CanonicalPhrase, JavaStep]] = []
    unmatched: List[CanonicalPhrase] = []
    for phrase in canonical:
        key = normalize_phrase(phrase.text)
        step = ref_index.get(key)
        if step is None:
            unmatched.append(phrase)
        else:
            matched.append((phrase, step))
    return matched, unmatched


# ============================================================
# Delta phrases YAML parsing (stdlib only)
# ============================================================

@dataclass
class DeltaPhrase:
    id: str
    text: str = ""
    description: str = ""
    recipe: str = ""
    ambiguous_with: List[str] = field(default_factory=list)


def parse_delta_yaml(yaml_text: str) -> List[DeltaPhrase]:
    """Parse simplified YAML delta-phrases block (line-based).

    Format:
        - id: G-001
          text: '...'
          description: ...
          recipe: |
            multiline
          ambiguous_with: [WC-001]
    """
    deltas: List[DeltaPhrase] = []
    current: Optional[DeltaPhrase] = None
    in_recipe = False
    recipe_lines: List[str] = []

    def _flush_recipe():
        nonlocal in_recipe, recipe_lines
        if current is not None and in_recipe:
            current.recipe = "\n".join(recipe_lines).rstrip()
        in_recipe = False
        recipe_lines = []

    def _commit():
        nonlocal current
        if current is not None:
            deltas.append(current)
        current = None

    for raw_line in yaml_text.splitlines():
        if in_recipe:
            stripped = raw_line.strip()
            if (
                raw_line.startswith("    ")
                or raw_line.startswith("\t")
                or stripped == ""
                or stripped.startswith("#")
            ):
                recipe_lines.append(raw_line[4:] if raw_line.startswith("    ") else raw_line)
                continue
            _flush_recipe()

        m_id = re.match(r"^-\s*id:\s*(\S+)\s*$", raw_line)
        if m_id:
            _commit()
            current = DeltaPhrase(id=m_id.group(1))
            continue
        if current is None:
            continue
        m_text = re.match(r"^\s+text:\s*[\"']?(.*?)[\"']?\s*$", raw_line)
        if m_text:
            current.text = m_text.group(1)
            continue
        m_desc = re.match(r"^\s+description:\s*(.*?)\s*$", raw_line)
        if m_desc:
            current.description = m_desc.group(1)
            continue
        m_recipe = re.match(r"^\s+recipe:\s*\|", raw_line)
        if m_recipe:
            in_recipe = True
            recipe_lines = []
            continue
        m_amb = re.match(r"^\s+ambiguous_with:\s*\[(.*)\]\s*$", raw_line)
        if m_amb:
            current.ambiguous_with = [x.strip() for x in m_amb.group(1).split(",") if x.strip()]
            continue
    if current is not None:
        _flush_recipe()
        _commit()
    return deltas


def extract_delta_block(design_text: str) -> str:
    """Extract YAML text between DELTA_MARKER_BEGIN and DELTA_MARKER_END."""
    begin = design_text.find(DELTA_MARKER_BEGIN)
    end = design_text.find(DELTA_MARKER_END)
    if begin == -1 or end == -1:
        return ""
    return design_text[begin + len(DELTA_MARKER_BEGIN):end]


# ============================================================
# Validation
# ============================================================

@dataclass
class ValidationResult:
    errors: List[str] = field(default_factory=list)
    warnings: List[str] = field(default_factory=list)

    @property
    def ok(self) -> bool:
        return not self.errors


def validate_delta(
    deltas: List[DeltaPhrase],
    canonical: List[CanonicalPhrase],
) -> ValidationResult:
    """Validate delta IDs: no conflict with canonical, monotonic IDs."""
    result = ValidationResult()
    canonical_ids = {p.id for p in canonical}
    canonical_texts = {normalize_phrase(p.text) for p in canonical}

    min_delta_num = {"G": 1, "W": 1, "T": 1}

    for d in deltas:
        # ID format
        m = re.match(r"^([GWT])-(\d+)([a-z]?)$", d.id)
        if not m:
            result.errors.append(f"Delta ID '{d.id}' does not match format [GWT]-XXX[a-z]?")
            continue
        letter, num_str, suffix = m.group(1), int(m.group(2)), m.group(3)
        # Conflict with canonical (canonical uses GC/WC/TC prefixes, delta uses G/W/T — no collision possible)
        if d.id in canonical_ids:
            result.errors.append(
                f"Delta ID '{d.id}' conflicts with existing canonical ID (canonical IDs are immutable)"
            )
        # Monotonic (only first ID of each category needs to be ≥ min)
        if not suffix and num_str < min_delta_num[letter]:
            result.errors.append(
                f"Delta ID '{d.id}' is below delta minimum {letter}-{min_delta_num[letter]:03d}"
            )
        # Ambiguity: delta text vs canonical text
        norm_delta = normalize_phrase(d.text)
        if norm_delta in canonical_texts:
            result.warnings.append(
                f"Delta ID '{d.id}' text duplicates canonical text structurally — possible AmbiguousStepDefinitions"
            )
    return result


def validate_canonical_complete(
    matched: List[tuple[CanonicalPhrase, JavaStep]],
    unmatched: List[CanonicalPhrase],
) -> ValidationResult:
    """Validate every canonical phrase is implemented in reference."""
    result = ValidationResult()
    if unmatched:
        ids = ", ".join(p.id for p in unmatched)
        result.errors.append(
            f"Canonical phrases not implemented in reference ({len(unmatched)}): {ids}. "
            f"Each canonical phrase MUST be implemented in reference-architecture (GAP to close)."
        )
    return result

# §2.3 generation
# ============================================================


def generate_phrase_mapping_table(
    matched: List[tuple[CanonicalPhrase, JavaStep]],
    deltas: List[DeltaPhrase],
) -> str:
    """Generate markdown table for §2.3."""
    lines: List[str] = []
    lines.append("| ID | Фраза | Источник | Реализация |")
    lines.append("|----|-------|----------|------------|")
    for phrase, step in sorted(matched, key=lambda x: x[0].id):
        impl = f"reference → {step.class_name}.{step.method_name}"
        lines.append(f"| {phrase.id} | `{phrase.text}` | canonical | {impl} |")
    for d in deltas:
        lines.append(f"| {d.id} | `{d.text}` | delta | implement по §2.2.1 |")
    return "\n".join(lines)


def replace_section(text: str, begin_marker: str, end_marker: str, new_content: str) -> str:
    """Replace content between markers (markers preserved)."""
    begin = text.find(begin_marker)
    end = text.find(end_marker)
    if begin == -1 or end == -1:
        raise ValueError(f"Markers not found: {begin_marker!r} / {end_marker!r}")
    return (
        text[: begin + len(begin_marker)]
        + "\n"
        + new_content
        + "\n"
        + text[end:]
    )

### 3.3. Предусловия, очистка и DB Write Approval

> **Принцип:** seed бизнес-сущностей виден аналитику в Gherkin (GC-004/GC-005); cleanup таблиц — техизоляция через hook (не загромождает Gherkin). Seed-фикстура локальна в каталоге-потребителе.

| Что | Как | Почему |
|-----|-----|--------|
| Seed бизнес-сущностей | GC-004 (`клиент создал ресурс через POST`) + GC-005 (`клиент сохранил response.X`) в Gherkin-сценарии | Аналитик видит предусловие в тексте теста. Фикстура локальна в `features/<feature-name>/request/<seed>.request.json` |
| Cleanup таблиц между сценариями | `@Before(order=20)` hook (SharedData_Steps) из `test.db.clean-tables` | Техизоляция: cleanup не загромождает Gherkin. Список — confirmation от пользователя |
| DB-seed справочников (исключение) | GC-007 (прямой SQL) — только если одобрено Gate: DB Write Approval | Справочники редко меняются, API для них может отсутствовать |
