Создать полную спецификацию сервиса — нового проектируемого или уже существующего в коде, но ещё **не описанного в `openspec/specs/`**. Двухэтапное интервью (ЧТО → КАК), затем генерация документа и ревью. Для правки уже существующей спеки используй `openspec-propose`.

**Input**: название сервиса и описание — либо только название, если пользователь хочет описать интерактивно.

**Bundle-пути.**

- Собственные `templates/X` и `references/X` — относительно директории этого скила.
- Внешние файлы из `openspec-explore` — **сосед по директории**, резолв через `<Skill dir>/../openspec-explore/references/<file>`.
- Если harness даёт строку `Skill directory: <abs>` в обёртке активации — используй её как корень для обоих. Например: `Read("<Skill dir>/templates/service-spec.md")`, `Read("<Skill dir>/../openspec-explore/references/invocation-contract.md")`.
- Если строки нет — один раз `Glob("**/openspec-skills/skills/openspec-new-spec/<file>")` и `Glob("**/openspec-skills/skills/openspec-explore/references/<file>")`, бери первый результат.
- Пусто → спроси пользователя путь установки, не ищи вручную по `~`/cwd.

**Bundled materials** (относительно этого SKILL.md):

- `templates/service-spec.md` — шаблон спецификации.
- `references/interview-playbook.md` — сценарий 2 этапов интервью.

**Scope исследования кода.** Лид **не читает код напрямую**. Оркестрирует субагентов по контракту из `openspec-explore/references/invocation-contract.md`. Скил `openspec-explore` как отдельный субагент **не запускается** — этот скил переиспользует его references.

**AskUserQuestion fallback**: если инструмент недоступен в клиенте — задай тот же вопрос обычным текстом и дождись ответа пользователя. Не угадывай.

## Steps

### 1. Этап 1 интервью — ЧТО за сервис

Без привязки к коду: потребители, функции, контекст, SLA. Не создавай спеку после одного вопроса. Детали и вопросы — `references/interview-playbook.md` (этап 1).

Из описания выведи kebab-case имя сервиса.

### 2. Изучи код — параллельные read-only субагенты

**Лид НЕ читает исходный код проекта напрямую** (ни Read, ни Grep, ни Glob, ни Serena по `src/**`, `app/**` и т. д.). 

**Что разрешено** лиду до запуска субагентов:
- Чтение OpenSpec-артефактов (`openspec/specs/**`, `openspec/changes/**`) — включая шаблон и существующие спеки для ориентира.
- Чтение собственных bundle-файлов (`templates/`, `references/`) и внешних explore-references (`<Skill dir>/../openspec-explore/references/*`).
- Быстрые bash-команды подсчёта файлов (`find … | wc -l`) без чтения содержимого — для классификации размера.

**После возврата субагентов** — точечный Read/Grep только для разрешения конкретной `gap` (≤3 файлов за раз).

**2.1. Прочитай шаблон и образцы.** `templates/service-spec.md` + 1–2 существующие спеки из `openspec/specs/` для ориентира формата.

**2.2. Прочитай канонический контракт.** Целиком: `openspec-explore/references/invocation-contract.md`. Там: обнаружение tool-а и `subagent_type` (§ 3.1), fallback-цепочка (§ 4), адаптация путей под стек (§ 5), валидация YAML (§ 6), дедупликация (§ 7), персистентность (§ 8). Дополнительно § 3 в `openspec-explore/references/research-orchestration.md` — группировка ролей для `target=spec` по размеру проекта.

**2.3. Собери параметры.**

- `target=spec`
- `service=<kebab-case>` (из Этапа 1)
- `roots` — корневые пути кода (спроси пользователя; для монорепо — путь модуля; для одного корня — `.`). Без `roots` не запускайся.
- `thoroughness=quick` (дефолт); `medium` только если пользователь явно сказал «подробнее» и проект крупный.

**2.4. Создай каталог.**

```bash
mkdir -p openspec/specs/<service>/.research
```

**2.5. Классифицируй размер и группу.** По § 2 в `research-orchestration.md`: <50 файлов = Малый (2 агента); 50–500 = Средний (2–3); >500 = Крупный (3–6). Группы ролей — § 3.1 того же файла.

**2.6. Прочитай промпты ролей.** Из `openspec-explore/references/research-roles.md` — секции `api`, `business-logic`, `data`, `integrations`, `config`, `observability`, `security`, `nfr`. **Копируй дословно**, не переформулируй «Цель / Границы / Формат вывода». Подставь реальные пути проекта в плейсхолдеры `<controllers/**>` и т.д. по таблице эвристик § 5 `invocation-contract.md`.

**2.7. Запусти субагентов — один ответ, один блок tool-use, несколько вызовов.**

Имя tool-а запуска субагента и `subagent_type` зависят от harness'а — **обнаружь по алгоритму § 3.1 `invocation-contract.md`** (регекс по списку доступных инструментов) и возьми значения из таблицы там же.

Параметры каждого вызова:
- `subagent_type` — read-only форма из таблицы § 3.1. При ошибке «unknown subagent type» — general-форма + блок «Дополнительные запреты» из § 4.
- `description` — 3–5 слов (`"Research api+business-logic+data"`).
- `prompt` — склеенные промпты ролей группы **дословно** с подставленными путями.
- `task_id` — **не использовать**.

Псевдокод (Малый/Средний — 2 группы; `<TOOL>`/`<ST>` — из § 3.1; реальный вызов через native tool-call API harness'а):

```
<TOOL>(subagent_type="<ST>", description="Research api+business-logic+data", prompt="<api + business-logic + data дословно, пути подставлены>")
<TOOL>(subagent_type="<ST>", description="Research integrations+config+obs+sec+nfr", prompt="<integrations + config + observability + security + nfr дословно>")
```

Последовательные вызовы в разных сообщениях = НЕ параллель, переделай.

Fallback: tool запуска субагента не найден → последовательный sweep по ролям (§ 4 шаг 3 `invocation-contract.md`), запиши в `.research/<role>.yaml` как если бы это сделал субагент.

**2.8. Запиши результаты, валидация, агрегация.**

1. Сохрани каждый возврат субагента в `.research/<role>.yaml` **до** валидации (§ 8.2 вариант A).
2. Валидируй YAML по § 6 (парсится, есть `summary`/`key_files` + доменные коллекции, summary ≤ 200 слов). Невалидно → одна попытка retry-промптом из § 6.
3. Склей коллекции и дедупни по ключам § 7.
4. Запиши `.research/_aggregate.yaml` + `.research-notes.md` (шаблон § 8.4).
5. Собранный `gaps[]` — вопросы для Этапа 2 интервью.

Не выходи со скила, пока 2.7 → 2.8 не выполнены целиком.

### 3. Этап 2 интервью — КАК устроен сервис

Теперь с агрегатом на руках: эндпоинты, бизнес-логика, интеграции, данные, авторизация, конфигурация. Привязывай вопросы к находкам из `.research-notes.md`. Подведи итог ВСЕХ данных и получи явное подтверждение перед переходом дальше. Категории вопросов и правила перехода — `references/interview-playbook.md` (этап 2).

### 4. Запиши спецификацию

Каталог `openspec/specs/<service>/` уже создан на шаге 2.4 (через `mkdir -p .../.research`). Запиши финальный документ в `openspec/specs/<service>/<service>.md`. Удали ВСЕ HTML-комментарии из шаблона, заполни все разделы реальным контентом. Большие файлы — по частям. Форматы блоков, уровни обязательности, ведение больших файлов — `references/section-guide.md`. Роль документа, что запрещено/допустимо — `references/guardrails.md`.

### 5. Ревью

Если доступен tool запуска субагента (имя и `subagent_type` — по таблице § 3.1 `openspec-explore/references/invocation-contract.md`) — запусти отдельный субагент с чеклистом. Иначе проведи ревью самостоятельно. Чеклист ревью и промпт субагента — `references/section-guide.md`. Исправь найденные проблемы и сообщи пользователю.

### 6. Очистка исследовательских артефактов

После успешной записи спеки (шаг 4) и ревью (шаг 5) — удали временные файлы исследования. Они нужны только до момента генерации документа; для будущих changes `openspec-propose` запустит `openspec-explore` заново со свежим состоянием кода.

**Через AskUserQuestion** спроси: удалить `.research/` и `.research-notes.md` или сохранить (если пользователь хочет ручной аудит собранных данных). Дефолт — удалить.

При подтверждении:

```bash
rm -rf openspec/specs/<service>/.research
rm -f openspec/specs/<service>/.research-notes.md
```

Если ревью (шаг 5) выявило проблемы, которые требуют повторного обращения к исследованию — **не чисти**, сначала исправь спеку, потом вернись к шагу 6.

# Правила ведения документации

Версия спецификации - 1.2

## 1. Общие требования

Вся документация должна вестись в Git.

В качестве формата используется простой GIGA IDEA + MarkDown.   
Для диаграмм последовательности GIGA IDEA + PlantUML.

## 2. Инструкция по созданию спецификации

1. В Bitbucket создается новая аналитическая ветка (Create branch -> Branch from: master -> Branch name: см. правила ниже).

2. Правило наименования веток в Git:

* при работе с фичами необходимо именовать ветку: **analytics/PROJECT-XXX/краткое описание
  задачи на английском без кавычек**
* при работе над багом: **bugfix/PROJECT-XXX/краткое описание задачи на
  английском без кавычек**

  где **PROJECT-XXX** - номер таски на аналитика в Jira/SberTrack.

3. В GIGA IDEA перейти на ветку master (Git -> выбрать master -> Checkout) и подтянуть изменения из удаленного репозитория (Git -> Update Selected).

4. Перейти на созданную ветку (Git -> выбрать ветку с PROJECT-XXX -> Checkout) и править документацию в рамках нее. 

5. После готовности документации все изменения необходимо запушить в удаленную ветку (Commit -> править описание коммита (см. ниже) -> Commit and Push).

6. При commit в удаленную ветку обязательно в описании коммита указывать **PROJECT-XXX** и краткое описание доработок на русском.

7. Согласование должно проходить с использованием PullRequest. Делать commit в ветку master минуя PullRequest **запрещено**!

8. В Bitbucket создается PullRequest (Create pull request -> Source: ветка с PROJECT-XXX -> Destination: master).   
   В наименовании PullRequest указать PROJECT-XXX + краткое описание на русском.  
   В описании PullRequest указать всю информацию, которая необходима проверяющему для корректной валидации.  
   В качестве согласующих ставятся:
   * Аналитик-проверяющий
   * Разработчик

9. После Approve от согласующих, аналитик самостоятельно делает Merge. Таска на аналитику закрывается, задача передается на разработку. 

10. В случае внесения правок в текущий PullRequest достаточно запушить правки в удаленную ветки и они автоматически подтянутся в открытый PullRequest.

## 3. Расположение документов

Спеки должны лежать в следующих папках:

* **protocols/protocolName** - спека с протоколами взаимодействия;
* **services/serviceName** - спека на сервисы.

В каждой папке должны быть созданы следующие подпапки:

* **/img** - картинки по plant uml
* **/plantUML** - исходники схем для plant uml
* **/schemas** - все схемы (можно создать подпапки по
  названиям сервисов если их много; может отсутствовать)
* **/examples** - примеры сообщений (может отсутствовать или быть подпапкой schemas)

## 1. Требования к логированию событий

### 1.1 Уровни логирования

Уровень события (Level) – один из заранее заданных уровней
важности события, выделяются следующие уровни:

- **OFF** - Логирование отключено. Никакие логи не записываются, все
  будут проигнорированы.
- **ERROR** - ошибка нормального функционирования, означающая отказ в
  обработке запроса и требующая реакции со стороны сопровождения. Может
  включать в себя: Непредусмотренные неверные сочетания параметров и
  условий, которые привели к невозможности обработать запрос и выдать
  логически корректный ответ Отсутствие требуемых ресурсов
  (недоступность системы хранения данных или внешних систем).
- **WARN** - возможная проблема в работе системы, которая может означать
  наличие других неявных проблем. Обычно не требует немедленной реакции
  со стороны поддержки. Может включать в себя:
    - Отказ в обработке всего или части запроса из-за неверных параметров
      (предусмотренные проверки на неверные сочетания параметров и условий),
      если в обычном случае параметры вызова должны генерироваться
      автоматически и такие неверные сочетания указывают на проблемы в
      сопряжённой системе;
    - Отказ в обработке из-за отсутствия у пользователя необходимых разрешений (не
      заменяет собой запись в журнале аудита и безопасности).
- **INFO** - «обычная» запись логирования событий, ожидаемые действия
  системы.
- **DEBUG** – запись в журнале событий, предназначенная для разбора
  проблемных ситуаций. Обычно уровень DEBUG отключён на
  production-системах, но включён на стендах тестирования для
  упрощения поиска ошибок. Может включать в себя самую разную информацию
  на усмотрение разработчика.
- **TRACE** - ещё более детальный по сравнению с DEBUG уровень. Обычно
  никогда не включается для всей системы, так как может привести к
  попытке регистрации каждого действия системы (в т.ч. одна строка кода
  = одно событие). Используется разработчиками на локальных стендах для
  локализации уже найденных проблем, один из инструментов отладки
  программы. Включается только на стендах тестирования.
- **ALL** - уровень, при котором будут записаны все логи из системы.

### 1.2 Настройка логирования

Процесс логирования настраивается через конфигурационный файл
и имеет несколько иерархичных уровней (Level):

- **DEBUG** - фиксируются события с уровнями: DEBUG, INFO, WARNING, ERROR;
- **INFO** - фиксируются события с уровнями: INFO, WARNING, ERROR;
- **WARN** - фиксируются события с уровнями: WARNING, ERROR;
- **ERROR** - фиксируются события с уровнями: ERROR;
- **TRACE** или **ALL** - все уровни.

Для формирования логов журнала используется библиотека [logback](https://logback.qos.ch/).

При формировании прикладного лога необходимо исключить возможность
попадания в него конфиденциальной информации K1/K2 (номера карт, номера
ДУЛ, фамилии, адреса и контактные данные клиентов и т.п.). В случае
наличия таких данных они должны "маскироваться" символами "*" перед
сохранением в лог.

## 2. Требования к кодам ошибок

## 3. Требования к кодам ошибок HTTP

Данный раздел определяет единый формат для возврата ошибок в HTTP API на основе
стандарта [RFC 9457 (ранее RFC 7807)](https://datatracker.ietf.org/doc/html/rfc9457) c целью обеспечения консистентности
и упрощения
обработки ошибок на стороне клиента.

* *Основной код состояния HTTP должен быть установлен в заголовке ответа.*
* *В теле ответа в поле **status** (если оно присутствует) должен быть указан код состояния HTTP `аналогичный` коду
  состояния HTTP в заголовке ответа.*
* *Для ответа используется application/problem+json*
* *В теле ответа используется JSON-объект в формате "Problem Detail*

### 3.3. HTTP-статусы ошибок AI Risk Hub

| Код   | Событие                           | Формат сообщения      |
|-------|-----------------------------------|-----------------------|
| `400` | Неправильный, некорректный запрос | Bad Request           |
| `403` | Недостаточно прав                 | Forbidden             |
| `404` | Ресурс не найден                  | Not Found             |
| `500` | Внутренняя ошибка сервера         | Internal Server Error |

### 3.2 Базовые атрибуты ответа кода ошибки

| Атрибут     | Тип данных | Обязательность | Описание                                                                                                                                                                          |
|-------------|------------|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `type`      | string     | [1]            | Ссылка URI, идентифицирующая тип проблемы.`Рекомендуется использовать относительные URI, начинающиеся с /problems/`                                                               |
| `title`     | string     | [1]            | Краткое, читаемое человеком резюме типа проблемы. <br/>Оно не должно меняться между несколькими случаями одного и того же типа проблемы, <br/>за исключением случаев локализации. |
| `status`    | number     | [1]            | Код статуса HTTP, сгенерированный исходным сервером. `Должен быть аналогичным коду статуса HTTP в заголовке ответа.`                                                              |
| `errorCode` | string     | [1]            | `Расширение` Человекочитаемый код ошибки                                                                                                                                          |
| `detail`    | string     | [0-1]          | Человекочитаемое описание возникновения этой конкретной проблемы.                                                                                                                 |
| `instance`  | string     | [0-1]          | URI, идентифицирующий ресурс, связанный с этим конкретным возникновением проблемы.                                                                                                |

**Примечание:** В соответствии с **RFC 9457**, если поле `type` в ответе об ошибке отсутствует или пустое, его значение
автоматически считается равным `"about:blank"`.
Это означает, что ошибка не имеет специальной семантики помимо стандартного HTTP-статуса.
Рекомендуется всегда явно указывать `type` — либо URI, либо `"about:blank"`.

### ПРАВИЛЬНО

- Бизнес-правила (2.3) — каждое правило ОБЯЗАНО содержать ДВЕ части: (1) ФОРМУЛИРОВКУ в формате ЕСЛИ / ТОГДА / ИНАЧЕ и/или математики; (2) ПОШАГОВЫЙ БИЗНЕС-ПСЕВДОКОД — нумерованные шаги с явной обработкой краёв (null, пустой ввод, округления, гонки). Псевдокод — на языке, независимом от реализации (без Java/Python/Go-синтаксиса, без аннотаций фреймворков, без обращений к коллекциям, потокам, библиотекам, кешам, индексам БД). ## Этап 1 — ЧТО за сервис (без привязки к коду)

Начни с открытого вопроса:
> "Какой сервис нужно документировать? Опишите его назначение и ключевые функции."

Далее — уточняющие вопросы порциями по 2–3:

- **Назначение**: "Кто потребители этого сервиса? Какую задачу он решает для бизнеса?"
- **Функции**: "Какие ключевые операции выполняет? Что самое важное?"
- **Контекст**: "Где этот сервис в общей архитектуре? Часть платформы, standalone?"
- **Надёжность**: "Какие SLA? Что происходит при недоступности зависимостей?"
- **Доменные сущности и термины**: "Какими доменными сущностями оперирует сервис? Есть ли специфические термины (например, «резервирование», «промокод»), которые нужно зафиксировать в глоссарии?"
- **Жизненный цикл**: "Есть ли у основной сущности явные статусы и правила переходов между ними (FSM)? Какие переходы разрешены, какие — нет?"
- **Бизнес-инварианты**: "Какие правила должны выполняться ВСЕГДА (например, «сумма скидки не больше суммы заказа»)? Что НИКОГДА не должно произойти?"

**Правила этапа 1:**
- Задавай вопросы порциями по 2–3, не заваливай стеной.
- Адаптируйся к ответам — если пользователь описал подробно, не переспрашивай очевидное.
- Если ответ неполный — копай глубже.
- **НЕ переходи к этапу 2**, пока назначение и контекст сервиса не ясны.
- Когда суть понятна — подведи итог и получи подтверждение.
- Из описания выведи kebab-case имя сервиса.

## Этап 2 — КАК устроен сервис (после изучения кода)

Теперь, зная назначение и изучив код, задавай вопросы по конкретным деталям:

- **API**: "Я вижу эндпоинты X, Y, Z в коде. Все актуальны? Есть ли незадокументированные?"
- **Типовой флоу клиента (2.1.1)**: "Какой типовой порядок API-вызовов у клиента от начала сценария до завершения? Например: сначала `GET /catalog`, затем `POST /orders`, затем `POST /orders/{id}/pay` — это полный флоу? Есть ли разные сценарии для разных клиентов (покупатель / администратор / автоматика)?" Если сервис чисто событийный (только consumer-ы и cron) — зафиксируй явно: «клиентского API нет».
- **Обработчики по триггерам (2.1.2.N)**: на КАЖДЫЙ обнаруженный триггер (endpoint / Kafka-consumer / cron / gRPC / SSE / webhook) задай вопросы по скелету:
  - «Что именно делает обработчик `<триггер>` пошагово?»
  - «Какие предусловия/guard должны быть выполнены до обработки?»
  - «Где транзакционные границы? Что коммитится атомарно, а что — отдельно? Что происходит при сбое на шаге N?»
  - «Какие side-effects (запись в БД, публикация в Kafka, внешние вызовы)?»
  - «Что возвращается клиенту / публикуется наружу?»
  - «Ошибочные ветки: какие коды ошибок и ссылки на альтернативные сценарии?»
  - «Идемпотентность: по какому ключу? Что происходит при повторе — возврат исходного результата, no-op, конфликт?»
- **Бизнес-логика и псевдокод (2.3)**: "В коде я нашёл правило X. Это верно? Опиши его как ПОШАГОВЫЙ алгоритм (нумерованные шаги) на конкретном примере: какие входные значения, какие промежуточные, какой выход. Как обрабатываются края — null, пустой ввод, округления, гонки?" Добивайся пошагового псевдокода для КАЖДОГО правила, даже линейного.
- **Бизнес-формулы**: "В коде расчёт суммы/скидки/тарифа выглядит как F(...). Это бизнес-формула в актуальной редакции? Округление, краевые значения? Покажи расчёт пошагово на конкретных числах."
- **FSM**: "В коде вижу переходы статусов A → B → C. Подтверди полный список разрешённых переходов и явно перечислим запрещённые. Что является триггером каждого перехода?"
- **Инварианты**: "Какие правила должны выполняться ВСЕГДА для основной сущности? Например, найденное в коде ограничение X — это инвариант или частный случай?"
- **Глоссарий**: "Термины X и Y используются в коде в разных местах — это одно и то же или разные понятия? Зафиксируем определение."
- **Интеграции**: "Сервис вызывает A и B. Это полный список? Как обрабатываются ошибки вызовов?"
- **Данные**: "Вижу сущности X, Y. Какие связи между ними? Есть ли кэширование?"
- **Авторизация**: "Какие роли имеют доступ? Есть ли ограничения по данным?"
- **Конфигурация**: "Вижу параметры X, Y в конфиге. Все документировать? Есть ли feature-флаги?"

**Правила этапа 2:**
- Привязывай вопросы к конкретике из кода — "Я вижу в коде X. Это актуально?"
- Если нашёл несоответствия или неочевидную логику — уточни.
- **НЕ переходи к созданию файла**, пока остаются неточности, неясности или недосказанности.
- Когда все детали разобраны — подведи итог ВСЕХ собранных данных и явно спроси: "Всё ли учтено? Есть ли что-то, что я упустил?"
- Только после подтверждения — переходи к созданию спецификации.
- Если при подтверждении пользователь добавляет новые детали — обработай их и снова подведи итог.

# Section Guide — заполнение service-spec.md

Как правильно заполнять разделы спецификации.

## Общие правила

- Удали ВСЕ HTML-комментарии (`<!-- ... -->`) из результата.
- Заполняй КАЖДЫЙ раздел реальным содержимым, без плейсхолдеров.
- Если раздел не применим (например, мониторинг для прототипа) — напиши: *"Не определено на текущем этапе. Будет добавлено при подготовке к production."*
- Записывай файл в `openspec/specs/<service-name>/<service-name>.md`.

## Уровни обязательности требований

- **ДОЛЖЕН / ОБЯЗАН** — обязательно, система не работает без этого.
- **СЛЕДУЕТ** — рекомендуется, допускается отступление с обоснованием.
- **МОЖЕТ** — опционально.

## Форматы ключевых блоков

- **Глоссарий (1.2)** — таблица «Термин / Синонимы / Определение». Каждый доменный термин, появляющийся в правилах, моделях, сценариях, обязан быть здесь.
- **Бизнес-инварианты (1.3)** — нумерованный список с формулировкой **ВСЕГДА** / **НИКОГДА**. Каждый инвариант наблюдаем (можно проверить тестом или запросом). Покрываются критериями приёмки в разделе 3.
- **Типовой флоу клиента (2.1.1)** — таблица «# / Шаг клиента / Endpoint / Зачем / Что клиент получил». Последовательность API-вызовов клиента от начала пользовательского сценария до завершения. Если сценариев несколько (покупатель/админ/оператор) — отдельная таблица на каждый. Если сервис чисто событийный — писать «Не применимо: сервис не имеет клиентского API».
- **Обработчики по триггерам (2.1.2.N)** — один подраздел на каждый триггер (HTTP endpoint / Kafka-consumer / cron / gRPC / SSE / webhook). Используется ФИКСИРОВАННЫЙ скелет: **Триггер, Инициатор, Вход, Предусловия (guard), Шаги обработки (нумерованные, со ссылками на 2.3 и 2.4), Side-effects, Выход/ответ, Ошибочные ветки (ссылка на 2.2 и 2.11), Идемпотентность (ключ и поведение при повторе)**. Пропуск любого поля скелета — замечание ревью. Это ядро «восстановимости» сервиса по спеке.
- **Бизнес-правила (2.3)** — каждое правило состоит из ДВУХ частей: (1) ФОРМУЛИРОВКА (ЕСЛИ/ТОГДА/ИНАЧЕ и/или математика); (2) ПОШАГОВЫЙ БИЗНЕС-ПСЕВДОКОД — нумерованные шаги с явной обработкой краёв (null, пустой ввод, округления, гонки). Псевдокод ОБЯЗАТЕЛЕН для КАЖДОГО правила (даже линейного). Язык — независимый от языка реализации (без Java/Python/Go-синтаксиса, без аннотаций фреймворков). Правила перехода статусов сюда НЕ включаются — они в 2.4 FSM.
- **FSM (2.4)** — таблица переходов (#, from, to, trigger, guard, side-effect) + список состояний с семантикой + явные запрещённые переходы + диаграмма (PlantUML/Mermaid). Если у сущности нет состояний — пишется «Не применимо для данного сервиса». Guard-условие в FSM ссылается на правило в 2.3, а не дублирует его.
- **Критерии приёмки (3)** — КОГДА / ТОГДА (примеры в шаблоне). Каждый переход FSM из 2.4 и каждый бизнес-инвариант из 1.3 ДОЛЖНЫ иметь хотя бы один критерий приёмки.
- **API** — метод, путь, request/response JSON-схема.
- **Модели данных** — таблица полей (имя, тип, обязательность, пример, описание).
- **Интеграции** — протокол, формат, таймаут, retry-политика.
- **Конфигурация** — таблица параметров (имя, тип, default, описание).

## Перекрёстные ссылки (ОБЯЗАТЕЛЬНО)

Спецификация должна быть прошита перекрёстными ссылками — это и есть главный механизм «восстановимости» сервиса по документу:

- Шаги клиентского флоу 2.1.1 со значимым переходом состояния → ссылка на переход **2.4.X**.
- Шаги обработчика 2.1.2.N со значимым решением → ссылка на правило **2.3.X** и/или переход **2.4.X**.
- Поле «Предусловия» обработчика 2.1.2.N → ссылка на инвариант **1.3.X** и/или переход **2.4.X**.
- Поле «Ошибочные ветки» обработчика 2.1.2.N → ссылка на сценарий **2.2.X** и/или код ошибки **2.11**.
- Альтернативные сценарии 2.2 → ссылка на правило **2.3.X** и/или переход **2.4.X**.
- Поля модели данных 2.7 со значениями статуса/типа → ссылка на 2.4 (для статусов) или на глоссарий 1.2 (для доменных типов).
- Конфигурационные параметры 2.8, влияющие на поведение, → ссылка на правило 2.3.X, переход 2.4.X, или обработчик 2.1.2.N.
- Критерии приёмки 3 → ссылка на переход FSM (2.4.X) или инвариант (1.3.X), который проверяет.
- Параметры аудита/безопасности 4.1, 4.5 → ссылка на инвариант 1.3.X.

Допустимый формат ссылки в тексте: `см. правило 2.3.X`, `см. переход 2.4.X`, `см. инвариант 1.3.X`, `см. глоссарий 1.2`, `см. обработчик 2.1.2.N`, `см. сценарий 2.2.X`.

## Большие файлы

Спецификация может получиться 300+ строк. Если файл большой — записывай его **по частям** (раздел за разделом), чтобы не потерять контент из-за ограничений контекстного окна. Предупреди пользователя: *"Спецификация объёмная, записываю по частям."*

## Ревью после создания

Проверь:

1. **Самодостаточность** — можно ли по одной спеке восстановить сервис с нуля, не имея доступа к исходному коду? Каждый раздел должен быть полным описанием, а не отсылкой к коду.
2. **Отсутствие утечек реализации** — нет ли ссылок на классы (`OrderService`), методы (`createOrder()`), пакеты (`com.shop.orders`), файлы исходного кода (`src/main/java/...`)? Допустимы только ссылки на контрактные артефакты (OpenAPI/proto/avro/JSON Schema/SQL DDL/диаграммы).
3. **Полнота** — все ли функции сервиса отражены? Нет ли пропущенных эндпоинтов, сущностей, интеграций, бизнес-правил?
4. **Точность** — соответствуют ли описания наблюдаемому поведению сервиса? Нет ли расхождений в названиях полей API, типах, форматах данных, кодах ошибок?
5. **Непротиворечивость** — нет ли конфликтов между разделами?
6. **Конкретность** — нет ли размытых формулировок, плейсхолдеров, TODO?
7. **Структура** — все ли обязательные разделы присутствуют и заполнены?
8. **Глоссарий** — каждый доменный термин из правил/моделей/сценариев определён в 1.2? Нет ли терминов, использующихся в разном смысле в разных разделах?
9. **Инварианты** — раздел 1.3 содержит нерушимые гарантии в формате ВСЕГДА/НИКОГДА? Каждый инвариант покрыт критерием приёмки в разделе 3?
10. **Типовой флоу клиента (2.1.1)** — присутствует таблица последовательности API-вызовов клиента? Для чисто событийных сервисов — явная пометка «Не применимо»? Шаги ссылаются на переходы 2.4.X при смене статуса сущности?
11. **Обработчики (2.1.2.N)** — на КАЖДЫЙ триггер сервиса (HTTP endpoint, Kafka-consumer, cron, gRPC, SSE, webhook) есть отдельный подраздел? В каждом заполнены ВСЕ поля скелета (Триггер, Инициатор, Вход, Предусловия, Шаги, Side-effects, Выход/ответ, Ошибочные ветки, Идемпотентность)? Нет ли триггеров, упомянутых в 2.5/2.6, но не имеющих обработчика в 2.1.2?
12. **Бизнес-правила (2.3)** — КАЖДОЕ правило содержит и ФОРМУЛИРОВКУ (ЕСЛИ/ТОГДА), и ПОШАГОВЫЙ ПСЕВДОКОД (нумерованные шаги)? Псевдокод без привязки к языку реализации? Края (null, округление, пустой ввод, гонки) явно обработаны?
13. **FSM** — если сервис управляет жизненным циклом сущности, раздел 2.4 содержит полную таблицу переходов и список запрещённых переходов? Нет ли неявных переходов, упомянутых в сценариях, но отсутствующих в FSM?
14. **Перекрёстные ссылки** — шаги обработчиков 2.1.2.N ссылаются на правила 2.3.X и переходы 2.4.X? Поле «Ошибочные ветки» ссылается на 2.2.X и 2.11? Критерии приёмки 3 ссылаются на FSM/инварианты?

Если доступен tool запуска субагента — запусти **отдельный субагент** с промптом:
> Проведи ревью файла `openspec/specs/<service-name>/<service-name>.md`. Ключевой критерий — **самодостаточность**: может ли разработчик реализовать сервис с нуля по одной этой спеке, не заглядывая в исходный код? Проверь дополнительно: (а) отсутствие утечек реализации (имена классов/методов/пакетов/файлов исходного кода недопустимы; ссылки на контракты — OpenAPI/proto/avro/SQL DDL/диаграммы — допустимы); (б) глоссарий 1.2 — каждый доменный термин определён; (в) инварианты 1.3 — нерушимые правила ВСЕГДА/НИКОГДА, каждый покрыт критерием приёмки; (г) 2.1.1 Типовой флоу клиента — таблица последовательности API-вызовов присутствует, либо явная пометка «Не применимо»; (д) 2.1.2.N Обработчики — на каждый триггер (endpoint/consumer/cron/gRPC/SSE/webhook) отдельный подраздел со ВСЕМИ полями скелета (Триггер, Инициатор, Вход, Предусловия, Шаги, Side-effects, Выход/ответ, Ошибочные ветки, Идемпотентность); (е) 2.3 Бизнес-правила — каждое правило имеет и формулировку, и пошаговый псевдокод без привязки к языку реализации; края (null, округление, гонки) явно обработаны; (ж) FSM 2.4 — полная таблица переходов и запрещённых переходов; (з) перекрёстные ссылки обработчик↔правило↔FSM↔инвариант↔критерий приёмки; (и) полноту, точность, непротиворечивость, конкретность, структуру. Верни список проблем или "Ревью пройдено, замечаний нет".

Если tool запуска субагента недоступен — проведи ревью самостоятельно по этому чеклисту.

Если найдены проблемы — исправь спецификацию и сообщи пользователю, что было исправлено.

## Output

После создания и ревью покажи:
- Название сервиса и путь к файлу.
- Список сгенерированных разделов.
- Ключевые задокументированные интеграции.
- Результат ревью (замечания и исправления, если были).
- Подсказку: *"Спецификация готова. Для внесения изменений запусти скилл `openspec-propose`."*

<!-- ПРИМЕР:
### Правила расчёта итоговой стоимости

1. **Расчёт `subtotal` для каждой позиции:**
   `subtotal[i] = items[i].price * items[i].quantity`

2. **Расчёт `originalAmount`:**
   `originalAmount = SUM(subtotal[i] for all i)`

3. **Расчёт `finalAmount` (после применения скидки):**
   ```
   IF promoCode применён И валиден:
       discountAmount = вычислить по правилу 2.3.4
       finalAmount = MAX(0, originalAmount - discountAmount)
   ELSE:
       discountAmount = 0
       finalAmount = originalAmount
   ```
   При округлении использовать BANKERS_ROUNDING до 2 знаков после запятой.

### Правила применения промокода

2. **ЕСЛИ** поле `promoCode` не передано или пустое,
   **ТОГДА** заказ оформляется по полным ценам, `discountAmount = 0`.

3. **ЕСЛИ** `promoCode` передан,
   **ТОГДА** проверить промокод в таблице `promo_codes`:
   - **ЕСЛИ** промокод не найден, **ТОГДА** вернуть ошибку 400 "Промокод не найден".
   - **ЕСЛИ** `valid_until < now()`, **ТОГДА** вернуть ошибку 400 "Срок действия промокода истёк".
   - **ЕСЛИ** `usage_count >= max_usages`, **ТОГДА** вернуть ошибку 400 "Промокод больше не действует".

4. **Расчёт скидки:**
   - **ЕСЛИ** `discount_type = 'PERCENT'`,
     **ТОГДА** `discountAmount = ROUND(originalAmount * discount_value / 100, 2)`.
   - **ЕСЛИ** `discount_type = 'FIXED'`,
     **ТОГДА** `discountAmount = MIN(discount_value, originalAmount)`.
   - В обоих случаях гарантируется инвариант 1.3.2 (`discountAmount <= originalAmount`).

### Правила резервирования товара

5. **ЕСЛИ** при создании заказа хотя бы один товар имеет `available_quantity < requested_quantity`,
   **ТОГДА** заказ НЕ создаётся, возвращается 409 CONFLICT со списком недоступных позиций.
   **ИНАЧЕ** для каждой позиции выполняется `available_quantity -= quantity` атомарно.

### Правила отправки уведомлений

6. **ЕСЛИ** заказ перешёл в статус `PAID` (см. переход 2.4.3),

   **ТОГДА** отправить событие `ORDERS.SHIPPED`.
8. **ЕСЛИ** заказ перешёл в статус `CANCELLED`,
   **ТОГДА** отправить событие `ORDERS.CANCELLED`.

# Правила ведения документации

Версия спецификации - 1.2

## 1. Общие требования

Вся документация должна вестись в Git.

В качестве формата используется простой GIGA IDEA + MarkDown.   
Для диаграмм последовательности GIGA IDEA + PlantUML.

## 2. Инструкция по созданию спецификации

1. В Bitbucket создается новая аналитическая ветка (Create branch -> Branch from: master -> Branch name: см. правила ниже).

2. Правило наименования веток в Git:

* при работе с фичами необходимо именовать ветку: **analytics/PROJECT-XXX/краткое описание
  задачи на английском без кавычек**
* при работе над багом: **bugfix/PROJECT-XXX/краткое описание задачи на
  английском без кавычек**

  где **PROJECT-XXX** - номер таски на аналитика в Jira/SberTrack.

3. В GIGA IDEA перейти на ветку master (Git -> выбрать master -> Checkout) и подтянуть изменения из удаленного репозитория (Git -> Update Selected).

4. Перейти на созданную ветку (Git -> выбрать ветку с PROJECT-XXX -> Checkout) и править документацию в рамках нее. 

5. После готовности документации все изменения необходимо запушить в удаленную ветку (Commit -> править описание коммита (см. ниже) -> Commit and Push).

6. При commit в удаленную ветку обязательно в описании коммита указывать **PROJECT-XXX** и краткое описание доработок на русском.

7. Согласование должно проходить с использованием PullRequest. Делать commit в ветку master минуя PullRequest **запрещено**!

8. В Bitbucket создается PullRequest (Create pull request -> Source: ветка с PROJECT-XXX -> Destination: master).   
   В наименовании PullRequest указать PROJECT-XXX + краткое описание на русском.  
   В описании PullRequest указать всю информацию, которая необходима проверяющему для корректной валидации.  
   В качестве согласующих ставятся:
   * Аналитик-проверяющий
   * Разработчик

9. После Approve от согласующих, аналитик самостоятельно делает Merge. Таска на аналитику закрывается, задача передается на разработку. 

10. В случае внесения правок в текущий PullRequest достаточно запушить правки в удаленную ветки и они автоматически подтянутся в открытый PullRequest.

## 3. Расположение документов

Спеки должны лежать в следующих папках:

* **protocols/protocolName** - спека с протоколами взаимодействия;
* **services/serviceName** - спека на сервисы.

В каждой папке должны быть созданы следующие подпапки:

* **/img** - картинки по plant uml
* **/plantUML** - исходники схем для plant uml
* **/schemas** - все схемы (можно создать подпапки по
  названиям сервисов если их много; может отсутствовать)
* **/examples** - примеры сообщений (может отсутствовать или быть подпапкой schemas)

# Примеры для change.md

Этот файл — каталог примеров заполнения для каждого из 13 разделов `change.md`. Примеры построены на сквозном сценарии «добавить систему промокодов в `order-service`».

**Как использовать**: при создании `change.md` не копируй примеры в результат. Используй их как ориентир формата и полноты. Все реальные значения должны быть взяты из контекста конкретного изменения. Полный готовый пример без плейсхолдеров лежит в `example-change.md` (рядом с этим файлом).

---

## 1. Предложение

### Цель изменения

Добавить систему промокодов в `order-service`, чтобы покупатели могли применять скидочные коды при оформлении заказа. Это позволит маркетингу запускать акции и увеличить конверсию оформления заказов на 15%.

### Инициатор

Команда маркетинга, тикет SHOP-1234. Проблема: нет механизма применения промокодов — акции приходится проводить вручную через изменение цен в каталоге.

### Затронутые компоненты

- [x] `order-service` — применение промокода при оформлении заказа, пересчёт суммы
- [x] `payment-service` — передача итоговой суммы со скидкой при оплате
- [ ] `notification-service` — отправка письма с деталями скидки (отдельный CR)

---

## 2. Бизнес-логика — правила применения промокода

1. При оформлении заказа клиент МОЖЕТ передать поле `promoCode` в запросе.

2. **ЕСЛИ** поле `promoCode` не передано или пустое, **ТОГДА** заказ оформляется по обычным ценам без скидки.

3. **ЕСЛИ** `promoCode` передан, **ТОГДА** `order-service` проверяет промокод в таблице `promo_codes`:
   - **ЕСЛИ** промокод не найден, **ТОГДА** вернуть ошибку `400` с сообщением «Промокод не найден».
   - **ЕСЛИ** промокод найден, но `valid_until < now()`, **ТОГДА** вернуть ошибку `400` «Срок действия промокода истёк».
   - **ЕСЛИ** промокод найден, но `usage_count >= max_usages`, **ТОГДА** вернуть ошибку `400` «Промокод больше не действует».
   - **ЕСЛИ** промокод валиден, **ТОГДА** применить скидку (см. правила расчёта ниже).

4. **ЕСЛИ** `discount_type = 'PERCENT'`, **ТОГДА** скидка = `total_amount * discount_value / 100`.
   **ЕСЛИ** `discount_type = 'FIXED'`, **ТОГДА** скидка = `discount_value` (в рублях).

5. **ЕСЛИ** рассчитанная скидка больше суммы заказа, **ТОГДА** скидка ограничивается суммой заказа (итого = 0, но не отрицательное).

6. После успешного применения:
   - `usage_count` в `promo_codes` увеличивается на 1;
   - в заказе сохраняется `promo_code_id` и `discount_amount`;
   - событие `ORDERS.CREATED` в Kafka содержит поля `promoCode` и `discountAmount`.

CREATE TABLE promo_codes (

  ]
}

## 7. Интеграции — ADDED

### REST

#### `POST /api/v1/orders/{orderId}/apply-promo` — Применение промокода

- **Описание**: Проверяет промокод и применяет скидку к указанному заказу.
- **Request**:
  ```json
  { "promoCode": "SUMMER2026" }
  ```
- **Response (200)**:
  ```json

    "orderId": "ord-123",

  ```
- **Таймаут**: 5000 мс
- **Retry**: нет (клиент повторяет вручную)

### Kafka

#### `ORDERS.CREATED` (обновлённый producer)

- **Описание**: Событие о создании заказа теперь включает информацию о промокоде.
- **Направление**: producer
- **Формат**: JSON (схема `OrderCreatedEvent`)
- **Таймаут**: 5000 мс (`delivery.timeout.ms`)
- **Retry**: встроенный retry Kafka producer

### gRPC

#### `PaymentService.CreatePayment`

```protobuf

```

- **Таймаут**: 10 000 мс
- **Retry**: 2 попытки, backoff 1 с / 3 с

### SSE

#### `GET /api/v1/orders/{orderId}/status-stream`

- **Описание**: Клиент подписывается на обновления статуса заказа в реальном времени.
- **Request**: `GET ...` с `Accept: text/event-stream`
- **Response**:
  ```
  event: ORDER_STATUS_CHANGED
  id: evt-001
  data: {"orderId": "ord-123", "status": "PAID", "updatedAt": "2026-04-03T12:00:00Z"}

  id: evt-002

  ```
- **Таймаут**: 300 000 мс (5 минут, затем переподключение)
- **Reconnect**: клиент переподключается с `Last-Event-ID`

### Cron

#### `expired-promo-codes-cleanup` — деактивация просроченных промокодов

- **Описание**: периодическая пометка просроченных промокодов как неактивных.
- **Расписание**: `0 0 1 * * *` (ежедневно в 01:00)
- **Окно**: 60 секунд
- **Max retry**: 3 попытки на batch
- **Backoff**: 5000 мс между попытками

## 11. Влияние на безопасность

- **Авторизация/аутентификация**: без изменений — промокод применяется только для авторизованных пользователей (JWT обязателен).
- **Новые роли/права**: роль `promo-manager` — создание и деактивация промокодов через admin API.
- **Маскирование данных**: промокоды не содержат PII — маскирование не требуется. `$.deliveryAddress` ДОЛЖЕН маскироваться в логах (первые 10 символов + `...`).

## 12. Миграция

### Шаги миграции данных

1. Создать таблицу `promo_codes` (см. раздел 6).
2. Добавить колонки `promo_code_id` и `discount_amount` в `orders` (`ALTER TABLE`).
3. Заполнить `discount_amount = 0` для всех существующих заказов (batch `UPDATE`).
4. Загрузить начальный набор промокодов от команды маркетинга (`INSERT`).

### Обратная совместимость API

- Переходный период: 2 спринта (4 недели).
- Поле `promoCode` в запросе — опциональное, старые клиенты работают без изменений.
- Поле `totalAmount` в ответе сохраняется (равно `finalAmount`).
- После окончания переходного периода `totalAmount` помечается `deprecated`.

### План отката

1. Отключить feature flag `shop.promo.enabled=false`.
2. Перезапустить поды `order-service`.
3. Таблицу `promo_codes` и новые колонки в `orders` оставить — не мешают работе.

## 1. Требования к логированию событий

### 1.1 Уровни логирования

Уровень события (Level) – один из заранее заданных уровней
важности события, выделяются следующие уровни:

- **OFF** - Логирование отключено. Никакие логи не записываются, все
  будут проигнорированы.
- **ERROR** - ошибка нормального функционирования, означающая отказ в
  обработке запроса и требующая реакции со стороны сопровождения. Может
  включать в себя: Непредусмотренные неверные сочетания параметров и
  условий, которые привели к невозможности обработать запрос и выдать
  логически корректный ответ Отсутствие требуемых ресурсов
  (недоступность системы хранения данных или внешних систем).
- **WARN** - возможная проблема в работе системы, которая может означать
  наличие других неявных проблем. Обычно не требует немедленной реакции
  со стороны поддержки. Может включать в себя:
    - Отказ в обработке всего или части запроса из-за неверных параметров
      (предусмотренные проверки на неверные сочетания параметров и условий),
      если в обычном случае параметры вызова должны генерироваться
      автоматически и такие неверные сочетания указывают на проблемы в
      сопряжённой системе;
    - Отказ в обработке из-за отсутствия у пользователя необходимых разрешений (не
      заменяет собой запись в журнале аудита и безопасности).
- **INFO** - «обычная» запись логирования событий, ожидаемые действия
  системы.
- **DEBUG** – запись в журнале событий, предназначенная для разбора
  проблемных ситуаций. Обычно уровень DEBUG отключён на
  production-системах, но включён на стендах тестирования для
  упрощения поиска ошибок. Может включать в себя самую разную информацию
  на усмотрение разработчика.
- **TRACE** - ещё более детальный по сравнению с DEBUG уровень. Обычно
  никогда не включается для всей системы, так как может привести к
  попытке регистрации каждого действия системы (в т.ч. одна строка кода
  = одно событие). Используется разработчиками на локальных стендах для
  локализации уже найденных проблем, один из инструментов отладки
  программы. Включается только на стендах тестирования.
- **ALL** - уровень, при котором будут записаны все логи из системы.

### 1.2 Настройка логирования

Процесс логирования настраивается через конфигурационный файл
и имеет несколько иерархичных уровней (Level):

- **DEBUG** - фиксируются события с уровнями: DEBUG, INFO, WARNING, ERROR;
- **INFO** - фиксируются события с уровнями: INFO, WARNING, ERROR;
- **WARN** - фиксируются события с уровнями: WARNING, ERROR;
- **ERROR** - фиксируются события с уровнями: ERROR;
- **TRACE** или **ALL** - все уровни.

Для формирования логов журнала используется библиотека [logback](https://logback.qos.ch/).

При формировании прикладного лога необходимо исключить возможность
попадания в него конфиденциальной информации K1/K2 (номера карт, номера
ДУЛ, фамилии, адреса и контактные данные клиентов и т.п.). В случае
наличия таких данных они должны "маскироваться" символами "*" перед
сохранением в лог.

## 2. Требования к кодам ошибок

### 2.1 Система кодирования

Коды должны следовать единой системе нумерации:

- 1000-1999: Коды ошибок (ERROR)
- 2000-2999: Предупреждения (WARN)
- 3000-3999: Информационные сообщения (INFO)
- 4000-4999: Отладочная информация (DEBUG)

### 2.2 Структура кода

X Y Z  
│ │ └── Уникальный идентификатор события (00-99)  
│ └────── Функциональный модуль (0-9)  
└──────── Тип события (1-ERROR, 2-WARN, 3-INFO, 4-DEBUG)

### 2.3 Зарезервированные диапазоны по модулям

| Модуль                        | Диапазон ERROR | Диапазон INFO | Описание модуля            |

## 3. Требования к кодам ошибок HTTP

Данный раздел определяет единый формат для возврата ошибок в HTTP API на основе
стандарта [RFC 9457 (ранее RFC 7807)](https://datatracker.ietf.org/doc/html/rfc9457) c целью обеспечения консистентности
и упрощения
обработки ошибок на стороне клиента.

* *Основной код состояния HTTP должен быть установлен в заголовке ответа.*
* *В теле ответа в поле **status** (если оно присутствует) должен быть указан код состояния HTTP `аналогичный` коду
  состояния HTTP в заголовке ответа.*
* *Для ответа используется application/problem+json*
* *В теле ответа используется JSON-объект в формате "Problem Detail*

### 3.3. HTTP-статусы ошибок AI Risk Hub

| Код   | Событие                           | Формат сообщения      |
|-------|-----------------------------------|-----------------------|
| `400` | Неправильный, некорректный запрос | Bad Request           |
| `403` | Недостаточно прав                 | Forbidden             |
| `404` | Ресурс не найден                  | Not Found             |
| `500` | Внутренняя ошибка сервера         | Internal Server Error |

### 3.2 Базовые атрибуты ответа кода ошибки

| Атрибут     | Тип данных | Обязательность | Описание                                                                                                                                                                          |
|-------------|------------|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `type`      | string     | [1]            | Ссылка URI, идентифицирующая тип проблемы.`Рекомендуется использовать относительные URI, начинающиеся с /problems/`                                                               |
| `title`     | string     | [1]            | Краткое, читаемое человеком резюме типа проблемы. <br/>Оно не должно меняться между несколькими случаями одного и того же типа проблемы, <br/>за исключением случаев локализации. |
| `status`    | number     | [1]            | Код статуса HTTP, сгенерированный исходным сервером. `Должен быть аналогичным коду статуса HTTP в заголовке ответа.`                                                              |
| `errorCode` | string     | [1]            | `Расширение` Человекочитаемый код ошибки                                                                                                                                          |
| `detail`    | string     | [0-1]          | Человекочитаемое описание возникновения этой конкретной проблемы.                                                                                                                 |
| `instance`  | string     | [0-1]          | URI, идентифицирующий ресурс, связанный с этим конкретным возникновением проблемы.                                                                                                |

**Примечание:** В соответствии с **RFC 9457**, если поле `type` в ответе об ошибке отсутствует или пустое, его значение
автоматически считается равным `"about:blank"`.
Это означает, что ошибка не имеет специальной семантики помимо стандартного HTTP-статуса.
Рекомендуется всегда явно указывать `type` — либо URI, либо `"about:blank"`.

## 1. Предложение

### Цель изменения

Добавить в notification-service функциональность пакетной отправки статусов уведомлений во внешние системы через webhook'и. 

**Проблемы, которые решаем:**
- Внешние системы-подписчики должны опрашивать notification-service через polling API для получения статусов уведомлений
- Высокая нагрузка на notification-service при частом polling от множества клиентов
- Задержки в получении статусов внешними системами (до интервала polling)
- Отсутствие push-механизма для информирования внешних систем о событиях

**Решение:**
- notification-service самостоятельно отправляет webhook'и во внешние системы при наступлении событий
- Пакетирование событий для снижения количества HTTP-вызовов
- Гарантированная доставка с retry-механизмом
- Гибкая настройка подписок на события

### Инициатор

Команда интеграции AI Risk Hub. Необходимость снижения нагрузки на notification-service и уменьшения задержек доставки статусов уведомлений во внешние системы.

### Затронутые компоненты

- [x] notification-service — основная функциональность webhook batch отправки
- [x] openspec/specs/notification-service/notification-service.md — дополнение спецификации
- [ ] external-consumer-services — адаптация внешних систем для приёма webhook'ов (отдельный CR)

### Приоритет

**Высокий** — критично для снижения нагрузки на систему и улучшения времени доставки событий.

### Обратная совместимость

**Да** — функциональность webhook'ов является дополнительной к существующим механизмам (SSE, Kafka, polling). 

Конфигурация по умолчанию отключена (`webhook.batch.enabled=false`), что сохраняет текущее поведение системы.

## 2. Бизнес-логика

### Правила отправки webhook'ов

1. **ЕСЛИ** `webhook.batch.enabled = true`, **ТОГДА**:
   - Сервис активирует механизм пакетной отправки webhook'ов
   - События накапливаются в батч до достижения `batch.size` или `batch.interval`
   - **ИНАЧЕ** webhook'и не отправляются (существующие механизмы работают штатно)

2. **ЕСЛИ** размер батча достигает `batch.size` (параметр `webhook.batch.size`), **ТОГДА**:
   - Батч немедленно отправляется всем настроенным подписчикам
   - Создаётся новый пустой батч

3. **ЕСЛИ** интервал времени достигает `batch.interval` (параметр `webhook.batch.interval-ms`), **ТОГДА**:
   - Накопленные события отправляются подписчикам (даже если батч не заполнен)
   - Создаётся новый пустой батч

4. **ЕСЛИ** событие имеет `priority = high`, **ТОГДА**:
   - Событие отправляется немедленно, без пакетирования
   - Пропускает очередь батча

### Правила маршрутизации webhook'ов

1. **ЕСЛИ** событие относится к каналу `channel`, **ТОГДА**:
   - Отправляется только подписчикам, указавшим этот канал в `subscribedChannels`
   - **ИНАЧЕ** событие игнорируется для данного подписчика

2. **ЕСЛИ** статус уведомления совпадает с `eventTypes` подписчика, **ТОГДА**:
   - Событие включается в батч для этого подписчика
   - **ИНАЧЕ** событие не отправляется этому подписчику

### Retry-механизм для webhook'ов

1. **ЕСЛИ** отправка webhook'а завершилась ошибкой (таймаут, HTTP 5xx, ошибка соединения), **ТОГДА**:
   - Увеличивается `attemptCount` для этого webhook'а
   - **ЕСЛИ** `attemptCount < webhook.retry.max-attempts`, **ТОГДА**:
     - Запланировать повторную попытку через `webhook.retry.backoff-ms * 2^attemptCount`
     - Использовать экспоненциальную задержку
   - **ИНАЧЕ**:
     - Статус webhook'а: FAILED
     - Событие перемещается в DLT-очередь `WEBHOOK.DLT`
     - Генерируется алерт в систему мониторинга

2. **ЕСЛИ** получен HTTP-статус 4xx (кроме 429), **ТОГДА**:
   - Повторные попытки НЕ выполняются
   - Статус webhook'а: FAILED (client error)
   - Запись в лог WARN

3. **ЕСЛИ** получен HTTP-статус 429 (Too Many Requests), **ТОГДА**:
   - Использовать значение хедера `Retry-After` для задержки
   - **ЕСЛИ** хедер отсутствует, **ТОГДА** использовать стандартный backoff

### Идемпотентность webhook'ов

1. Каждый webhook содержит уникальный `webhookId` (UUID)
2. **ЕСЛИ** подписчик получил дублирующийся `webhookId`, **ТОГДА**:
   - Должен вернуть HTTP 200/201 без повторной обработки
   - Должен использовать `webhookId` для дедупликации

## 9. Хедеры и метаданные

### HTTP-хедеры для webhook'ов (исходящие)

| Операция | Транспорт | Имя | Направление | Обязательность | Формат | Пример | Назначение |
|----------|-----------|-----|-------------|---------------|--------|--------|-----------|
| ADDED | HTTP | Content-Type | request | required | string | application/json | Тип содержимого |
| ADDED | HTTP | X-Webhook-Signature | request | required | string | sha256=abc123... | HMAC-SHA256 подпись тела |
| ADDED | HTTP | X-Webhook-ID | request | required | UUID | webhook-uuid-99999 | Уникальный ID webhook'а |
| ADDED | HTTP | X-Webhook-Timestamp | request | required | timestamp (ms) | 1711929605000 | Время отправки |
| ADDED | HTTP | X-Subscription-ID | request | required | UUID | sub-uuid-12345 | ID подписки |
| ADDED | HTTP | User-Agent | request | required | string | notification-service/1.0 | Идентификация отправителя |
| ADDED | HTTP | X-Custom-* | request | optional | string | из конфигурации | Кастомные хедеры из подписки |

### HMAC-подпись webhook'ов

**Алгоритм:**
1. Тело запроса (JSON) берётся в исходном виде (raw bytes)
2. Вычисляется HMAC-SHA256 с использованием `secret` из подписки
3. Результат кодируется в hex (lowercase)
4. Добавляется префикс `sha256=`

**Пример:**
```
X-Webhook-Signature: sha256=6d2c85f3b8e9a1c4d7e0f2a5b8c1d4e7f0a3b6c9d2e5f8a1b4c7d0e3f6a9b2c5
```

**Валидация на стороне получателя:**
1. Получить значение хедера `X-Webhook-Signature`, отбросить префикс `sha256=`
2. Вычислить HMAC-SHA256 от тела запроса (raw bytes) с использованием `secret` из подписки
3. Сравнить вычисленную подпись с полученной (constant-time comparison для защиты от timing-атак)
4. Если подписи совпадают — запрос валиден, иначе — отклонить с HTTP 403

## 11. Влияние на безопасность

- **Авторизация/аутентификация**: 
  - API управления подписками требует JWT-токен с ролью `webhook-manager`
  - Проверка прав доступа при создании/обновлении/удалении подписок
  
- **Новые роли/права**:
  - `webhook-manager` — право управления webhook-подписками (CRUD)
  - `webhook-viewer` — право только на чтение подписок (GET)

- **Маскирование данных**:
  - Поле `recipient` в событиях webhook ДОЛЖНО маскироваться:
    - Email: `u***@example.com` (первая буква + `***@domain`)
    - Phone: `+7***1234567` (первые 3 символа + `***` + последние 4)
  - Секрет `secret` НЕ ДОЛЖЕН записываться в логи (маскирование 100%)
  - Поля K1/K2 в `metadata` ДОЛЖНЫ маскироваться согласно common-requirements.md

- **HMAC-подпись**:
  - Все webhook'и ДОЛЖНЫ быть подписаны HMAC-SHA256
  - Секрет хранится в зашифрованном виде в Cassandra (AES-256)
  - Передача секрета только при создании подписки (не возвращается в API)

## 12. Миграция

**Не требуется** — функциональность является дополнительной и включается конфигурацией.

### План включения (опционально)

1. Развернуть новую версию notification-service с feature flag `webhook.batch.enabled=false`
2. Настроить подписки через API для тестовых сред
3. Протестировать доставку webhook'ов на staging
4. Включить `webhook.batch.enabled=true` на production
5. Мониторить метрики доставки и ошибок

### План отката

1. Установить `webhook.batch.enabled=false`
2. Перезапустить поды notification-service
3. Существующие подписки сохраняются в БД (неактивны)

| 6 | Webhook endpoint вернул HTTP 200 | Статус батча: SENT, метрика webhook_events_delivered_total инкрементирована |
| 7 | Webhook endpoint вернул HTTP 500 (таймаут) | Выполняется retry до 5 попыток с экспоненциальной задержкой, статус: RETRYING |
| 8 | Все retry попытки исчерпаны (5 раз ошибка) | Статус батча: FAILED, запись в WEBHOOK.DLT, метрика webhook_dlt_count инкрементирована, алерт в мониторинг |
| 9 | Webhook endpoint вернул HTTP 400 | Retry НЕ выполняются, статус: FAILED (client error), запись в лог WARN |
| 10 | Webhook endpoint вернул HTTP 429 с хедером Retry-After: 60 | Следующая попытка через 60 секунд, запись в лог WARN |
| 11 | Событие имеет priority=high | Отправлено немедленно без пакетирования, вне очереди батча |
| 12 | Получатель webhook'а проверяет HMAC-подпись | Подпись валидна при использовании правильного secret из подписки |
| 13 | В батче содержится событие с каналом "email", а подписчик подписан только на "push" | Событие НЕ включается в батч для этого подписчика |
| 14 | Подписка деактивирована (active=false) | События НЕ отправляются этому подписчику, батч не формируется |
| 15 | Feature flag webhook.batch.enabled=false | Webhook'и не отправляются ни при каких условиях, API управления подписками недоступно (404) |

# Guardrails — qualitative checklist для change.md

Подробный чеклист качества и запретов. Применяй перед фиксацией change.md и при ревью.

---

## Роль документа — КРИТИЧНО

`change.md` — документ **системного аналитика**, а не разработчика.
Описывай **ЧТО** должно измениться и **ЗАЧЕМ**, но **НИКОГДА** не пиши **КАК** реализовать в коде.

### ЗАПРЕЩЕНО включать в change.md

- Код на любом языке приложения (Java, Kotlin, Python, Go, JS/TS и т.д.)
- Реализацию методов, классов, функций
- Unit-тесты, integration-тесты, тестовый код любого вида
- Конкретные алгоритмические решения — это задача разработчика
- План внедрения с техническими шагами реализации
- Диаграммы классов, code-review замечания
- Конфигурационные файлы целиком (`application.yaml`, `.properties`, `.env`)
- **Ссылки на объекты исходного кода**: имена классов (`OrderService`), методов (`createOrder()`), пакетов (`com.shop.orders`), бинов, модулей
- **Ссылки на файлы исходного кода**: `src/main/java/...`, `pkg/handlers/...`, `app/services/...` и подобные пути к реализации

### РАЗРЕШЕНО

- Бизнес-правила (раздел 2) — каждое правило ОБЯЗАНО содержать (1) формулировку **ЕСЛИ/ТОГДА/ИНАЧЕ** и/или математику и (2) **пошаговый бизнес-псевдокод** с явной обработкой краёв (null, округления, гонки) — на языке, независимом от реализации (без Java/Python/Go-синтаксиса, без аннотаций фреймворков, без обращений к коллекциям, потокам, кешам, индексам БД). Технический псевдокод — запрещён, это территория архитектора.
- **Обработчики по триггерам (раздел 7А)** — на каждый новый/изменяемый триггер (HTTP endpoint / Kafka-consumer / cron / gRPC / SSE / webhook) фиксированный скелет: Триггер, Инициатор, Вход, Предусловия (guard), Шаги обработки, Side-effects, Выход/ответ, Ошибочные ветки, Идемпотентность. Для MODIFIED — обязательно «Шаги (было)» и «Шаги (стало)» либо явный diff по полям скелета. Допустимо указывать транзакционную границу на бизнес-уровне («атомарно в транзакции», «outbox», «saga») без упоминания конкретных фреймворков.
- **Флоу клиента (подраздел 1.5)** — изменения в типовой последовательности API-вызовов клиента: таблицы ADDED/MODIFIED/REMOVED. Если флоу не меняется — «Нет изменений».
- Модели данных как **таблицы полей** (имя, тип, обязательность, пример, описание)
- API как описание эндпоинтов (метод, путь, request/response **схема**), а не реализация
- Рекомендации к критериям приёмки в формате **КОГДА/ТОГДА** (без тестового кода)
- Конфигурация как **таблица параметров**, а не как yaml/properties-файл
- **SQL** — ТОЛЬКО как рекомендации по DDL/DML (`CREATE TABLE`, `ALTER TABLE`) для структуры данных
- **JSON-schema**, **Protobuf**, **Avro** — для описания моделей данных
- Описательные диаграммы потоков/состояний (PlantUML/Mermaid) — если они про домен, не про реализацию

### Допустимые ссылки на артефакты-контракты

Change **может и должен** ссылаться на контрактные артефакты (они описывают поведение, а не реализацию):

- **OpenAPI/Swagger**, **Protobuf**, **Avro**, **JSON Schema**, **GraphQL SDL**
- **SQL DDL / migrations** (`migration/V3__add_promo_codes.sql`, `db/changelog.yaml`)
- **XSD / WSDL**
- **Диаграммы поведения**: PlantUML/Mermaid (sequence, activity, state) — про домен, не про классы

**Ключевое отличие**: контракт описывает **поведение интерфейса** — он самодостаточен. Класс/метод/файл исходного кода описывает **реализацию** — без кода бесполезен.

### Если пользователь просит добавить код

Объясни: change.md описывает **требования**, а реализация — задача разработчика на основе этих требований. Реализация и код — в следующих скиллах (`openspec-design`, `openspec-implement`).

---

## Процесс — обязательные правила

- **НИКОГДА** не создавай change.md, пока остаются неясности — проведи полноценное интервью (см. `interview-playbook.md`) до полной ясности.
- **ВСЕГДА** изучи целевую спецификацию **ПЕРЕД** созданием change.md.
- Перед созданием файла **подведи итог ВСЕХ требований** и получи **явное подтверждение** пользователя.
- **НЕ копируй** примеры из шаблона/references в итоговый файл.
- Каждый заполненный раздел должен содержать **реальные данные**, а не плейсхолдеры и не TODO.
- Формулировки **ДОЛЖЕН/ОБЯЗАН** для обязательных требований; **СЛЕДУЕТ** для рекомендованных; **МОЖЕТ** для опциональных.
- Если change с таким именем уже существует — **спроси**, продолжить его или создать новый.
- После создания проверь: файл существует, все 16 основных разделов плюс 1.5 (Флоу клиента) и 7А (Обработчики) на месте, незатронутые помечены `Нет изменений.`.

---

## Ревью change.md (чеклист)

1. **Полнота** — все ли аспекты задачи покрыты? Нет ли пропущенных разделов, которые должны быть заполнены?
2. **Точность** — соответствуют ли описанные изменения наблюдаемому поведению текущего сервиса и согласуются ли с целевой спекой?
3. **Непротиворечивость** — нет ли конфликтов между разделами внутри change.md?
4. **Конкретность** — нет ли размытых формулировок, плейсхолдеров, TODO?
5. **Реализуемость** — возможно ли реализовать описанное? Нет ли пропущенных зависимостей?
6. **Границы роли** — нет ли кода приложения, unit-тестов, реализационных деталей? Нет ли ссылок на классы/методы/пакеты/файлы исходного кода? Ссылки допустимы только на контрактные артефакты (OpenAPI/proto/avro/SQL DDL/диаграммы поведения). Бизнес-псевдокод в разделе 2 — разрешён и требуется; технический псевдокод (блокировки, потоки, кеши, индексы БД) — запрещён.
7. **Форматы** — ЕСЛИ/ТОГДА/ИНАЧЕ + пошаговый псевдокод для бизнес-правил, КОГДА/ТОГДА для критериев приёмки.
8. **Флоу клиента (1.5)** — если change затрагивает порядок API-вызовов клиента, подраздел заполнен таблицами ADDED/MODIFIED/REMOVED; иначе — явное «Нет изменений».
9. **Обработчики (7А)** — если change добавляет/меняет/удаляет триггер (endpoint/consumer/cron/gRPC/SSE/webhook), раздел 7А содержит соответствующий подраздел со ВСЕМИ полями скелета (Триггер, Инициатор, Вход, Предусловия, Шаги, Side-effects, Выход, Ошибочные ветки, Идемпотентность). Для MODIFIED — есть «Шаги (было)» и «Шаги (стало)».

Верни результат: список найденных проблем или «Ревью пройдено, замечаний нет».

# Interview Playbook — openspec-propose

Подробные сценарии двух этапов интервью. Читай этот файл, когда нужен детальный разбор вопросов и правил перехода между этапами.

---

## Этап 1 — ЧТО и ЗАЧЕМ (без кода)

**Цель**: понять суть задачи, мотивацию, скоуп, ожидаемый результат. БЕЗ привязки к существующему коду и спецификациям.

### Начальный вопрос (открытый)

> «Какое изменение нужно внести? Опиши, что хочешь изменить и зачем.»

### Категории уточняющих вопросов

- **Мотивация**: «Какую проблему это решает? Кто столкнулся с ней? Как сейчас живут без этого?»
- **Скоуп**: «Это затрагивает только один сервис или несколько? Какие? Есть ли внешние системы?»
- **Пользователи**: «Кто использует эту функциональность? Внутренние пользователи, внешние клиенты, автоматика?»
- **Бизнес-логика**: «Какие правила должны работать? Есть ли исключения, крайние случаи?»
- **Ожидаемый результат**: «Как должно работать после изменения? Как пользователь это увидит?»
- **Ограничения**: «Есть ли дедлайны, зависимости от других команд, технические ограничения?»

### Правила этапа 1

- Задавай вопросы **порциями по 2–3**, не заваливай стеной.
- Адаптируйся к ответам — если пользователь описал подробно, не переспрашивай очевидное.
- Если ответ неполный или противоречивый — копай глубже: «Ты сказал X, но раньше упомянул Y — как это вместе?».
- **НЕ ПЕРЕХОДИ к этапу 2**, пока суть задачи не ясна полностью.
- Когда задача понятна — подведи итог своими словами и получи явное подтверждение.

### Выведение kebab-case имени

Из описания выведи имя: слова через дефис, маленькими латинскими буквами.

- «добавить batch webhook отправку» → `add-webhook-batch`
- «исправить валидацию email» → `fix-email-validation`
- «рефакторинг модуля авторизации» → `refactor-auth-module`

---

## Этап 2 — КАК именно меняем (привязка к коду/спеке)

**Цель**: после изучения кода и спецификаций задать предметные вопросы по деталям реализации изменения.

### Категории уточняющих вопросов

- **Флоу клиента (раздел 1.5 change, зеркало 2.1.1 спеки)**: «Меняется ли типовой порядок API-вызовов клиента? Добавляются/удаляются шаги? Появляется новый endpoint в середине флоу? Если да — опиши полный новый порядок и что возвращает каждый шаг.» Если флоу не меняется — зафиксируй «Нет изменений».
- **Обработчики по триггерам (раздел 7А change, зеркало 2.1.2 спеки)**: на КАЖДЫЙ новый или изменяемый триггер (HTTP endpoint / Kafka-consumer / cron / gRPC / SSE / webhook) пройдись по скелету:
  - «Что делает новый обработчик `<триггер>` пошагово? Какие предусловия (guard)?»
  - «Транзакционные границы: что коммитится атомарно, что отдельно? Что при сбое на шаге N?»
  - «Side-effects: БД, Kafka, внешние вызовы?»
  - «Что возвращается / публикуется?»
  - «Ошибочные ветки и коды ошибок?»
  - «Идемпотентность: ключ и поведение при повторе?»
  Для MODIFIED-обработчиков требуй «Было» и «Стало» пошагово.
- **Бизнес-логика и псевдокод (раздел 2)**: для КАЖДОГО нового/изменённого правила — добейся пошагового бизнес-псевдокода (нумерованные шаги, обработка краёв — null, округления, гонки) в дополнение к формулировке ЕСЛИ/ТОГДА. Проверяй на конкретном примере: вход → промежуточные значения → выход.
- **Модели данных**: «Сейчас в сущности X есть поля A, B, C. Нужны новые? Что-то меняется? Типы, обязательность?»
- **Интеграции**: «Сервис сейчас вызывает Y и Z. Появляются новые вызовы? Меняются существующие? Новые контракты?»
- **Ошибки**: «Какие новые ошибки возможны? Как их обрабатывать? Retry, DLQ, алерты?»
- **Миграция**: «В таблице X сейчас N записей. Нужна миграция данных? Обратная совместимость? План выката?»
- **Безопасность**: «Меняется доступ, роли, авторизация? Новые permissions?»
- **Конфигурация**: «Нужны новые параметры конфигурации? Feature-флаги? Значения по умолчанию?»
- **Мониторинг**: «Нужны новые метрики или алерты? SLA/SLO затронуты?»

### Правила этапа 2

- Привязывай вопросы к конкретике из кода и спецификаций — формулируй «Сейчас работает так: ... Как это должно измениться?».
- Если нашёл **противоречия** между задачей и текущей реализацией — обрати на них внимание явно.
- **НЕ ПЕРЕХОДИ к созданию файла**, пока остаются неточности, неясности или недосказанности.
- Когда все детали разобраны — подведи итог **ВСЕХ** собранных требований и спроси явно: «Всё ли учтено? Есть ли что-то, что я упустил?»
- Только после подтверждения пользователя — переходи к созданию change.md.
- Если пользователь при подтверждении добавляет новые детали — обработай их и **снова** подведи итог.

---

## Когда переходить дальше

| Этап | Критерий выхода |
|---|---|
| 1 → изучение контекста | Суть задачи ясна; kebab-case имя выведено; пользователь подтвердил понимание. |
| Изучение контекста → 2 | Прочитаны целевая спека, связанные спеки, ключевой код; известна текущая реализация. |
| 2 → создание change.md | Все детали реализации зафиксированы; пользователь явно подтвердил полноту списка требований. |

# Section Guide — заполнение change.md

Детальный guide по каждому разделу шаблона `../templates/change.md` (16 основных разделов + подраздел 1.5 «Флоу клиента» + дополнительный раздел 7А «Обработчики по триггерам»). Используй при заполнении: что ожидается, частые ошибки, форматы. Реальные сниппеты и форматы — в `change-examples.md` и `example-change.md` (рядом с этим файлом).

---

## Общие правила для всех разделов

- Если раздел **не затрагивается** изменением — пиши ровно одну строку: `Нет изменений.`
- Если используешь шаблон — **удали ВСЕ HTML-комментарии** (`<!-- -->`) из итогового файла.
- Примеры из соседних reference-файлов берутся **только как ориентир формата** — **никогда не копируй содержимое** примеров в итоговый файл.
- Заполненный раздел содержит **реальные данные текущего change**, без плейсхолдеров и TODO.

## Цветовые маркеры (Markdown/HTML)

- `<font color="red">**Alt**</font>` — альтернативный/ошибочный поток
- `<font color="blue">**Opt**</font>` — опциональный элемент
- `<font color="blue">**Loop**</font>` — циклический элемент
- `<font color="green">**Примечание:**</font>` — важные примечания

## Уровни обязательности требований

- **ДОЛЖЕН / ОБЯЗАН** — обязательно, система не работает без этого
- **СЛЕДУЕТ** — рекомендуется, но допускается отступление с обоснованием
- **МОЖЕТ** — опционально

---

## Шапка (метаданные)

Заполни: имя change, целевая спецификация, статус (`На согласовании` при создании), дата, автор. Остальные статусы (`Согласовано`, `В работе`, `Реализовано`, `Заархивировано`) проставляются вручную в дальнейшем воркфлоу.

---

## 1. Предложение

Ожидается: цель изменения (ЗАЧЕМ, бизнес-мотивация), инициатор, затронутые компоненты, приоритет, обратная совместимость. Дополнительно — **Флоу клиента (ADDED/MODIFIED/REMOVED)** в формате трёх таблиц: изменения в типовой последовательности API-вызовов клиента (зеркалит раздел 2.1.1 целевой спеки). Если флоу не меняется — одна строка «Нет изменений».
Частые ошибки: технические детали в цели вместо бизнес-мотивации; неопределённое «нужно улучшить X»; пропущенный инициатор; не отмечены компоненты влияния; флоу клиента не заполнен, когда change добавляет/удаляет endpoint или меняет порядок вызовов.
Формат цели: 2–5 абзацев на человеческом языке, без кода.

## 2. Бизнес-логика

Ожидается: пронумерованные правила. Каждое правило — ДВЕ части: (1) ФОРМУЛИРОВКА в формате ЕСЛИ/ТОГДА/ИНАЧЕ и/или математическая запись; (2) ПОШАГОВЫЙ БИЗНЕС-ПСЕВДОКОД — нумерованные шаги с явной обработкой краёв (null, пустой ввод, округления, гонки). Псевдокод ОБЯЗАТЕЛЕН для КАЖДОГО правила (даже линейного). Язык — независимый от языка реализации.
Частые ошибки: описание кода вместо правил; отсутствие пошагового псевдокода; пропущенные крайние случаи (null, округление, гонки); правила перехода статусов внутри 2 (они должны быть в разделе 5 FSM).

## 3. Глоссарий

Ожидается: ADDED / MODIFIED / REMOVED для доменных терминов. Термины из таблицы попадают в раздел 1.2 целевой спеки.
Частые ошибки: добавление термина без определения; разные определения одного термина в разных разделах change.md.

## 4. Бизнес-инварианты

Ожидается: ADDED / MODIFIED / REMOVED для нерушимых правил. Формулировка ВСЕГДА / НИКОГДА. Каждый инвариант наблюдаем (можно проверить тестом или запросом). В колонке «Покрывающий критерий приёмки» — ссылка на № в разделе 16.
Частые ошибки: размытая формулировка («нужно обеспечивать корректность»); инвариант без покрытия в критериях приёмки.

## 5. Состояния и переходы (FSM)

Ожидается: ADDED / MODIFIED / REMOVED для состояний и переходов. Таблица переходов: #, сущность, FROM, TO, триггер, guard (со ссылкой на правило в 2), side-effect. Отдельно — изменения списка запрещённых переходов.
Если сервис не управляет жизненным циклом сущности — пишется «Нет изменений».
Частые ошибки: добавление перехода без триггера и guard; решающая бизнес-логика внутри FSM (она должна быть в 2 + ссылка из guard).

## 6. Модели данных

Ожидается: таблицы полей (имя, тип, обязательность, пример значения, описание). JSON-schema/Protobuf/Avro допустимы.
SQL — ТОЛЬКО как DDL/DML-рекомендации (`CREATE TABLE`, `ALTER TABLE`) для описания структуры.
Все доменные термины в моделях должны соответствовать глоссарию (раздел 3).
Частые ошибки: вставка Java/Python-классов с аннотациями.

## 7. Интеграции

Ожидается: эндпоинты (метод, путь), request/response схемы, коды ответов, заголовки, примеры полезной нагрузки. Для внешних интеграций — контракт и направление вызова, таймаут, retry.
Частые ошибки: реализация контроллеров вместо контрактов; смешивание контракта и поведения обработчика (поведение идёт в 7А).

## 7А. Обработчики (по триггерам)

Ожидается: изменения в обработчиках по триггерам (зеркалит раздел 2.1.2 целевой спеки). Три секции — ADDED / MODIFIED / REMOVED. На каждый триггер (HTTP endpoint / Kafka-consumer / cron / gRPC / SSE / webhook) — отдельный подраздел с ФИКСИРОВАННЫМ скелетом: **Триггер, Инициатор, Вход, Предусловия (guard), Шаги обработки, Side-effects, Выход/ответ, Ошибочные ветки, Идемпотентность**. Для MODIFIED — обязательно «Шаги (было)» и «Шаги (стало)» либо явный diff по конкретным полям скелета. Если изменения не затрагивают обработчики — одна строка «Нет изменений».
Частые ошибки: пропущен какой-то триггер, затрагиваемый change; только описание контракта без пошагового поведения (контракт идёт в 7, поведение — в 7А); отсутствие поля «Идемпотентность»; для MODIFIED — отсутствие «было/стало».

## 8. Обработка ошибок

Ожидается: перечень ошибок (код, HTTP-статус, errorCode, ситуация), формат по RFC 7807 из `common-requirements.md`.
Частые ошибки: код `try/catch` вместо описания.

## 9. Хедеры и метаданные

Ожидается: таблица операций ADDED/MODIFIED/REMOVED по транспортам (HTTP/Kafka/gRPC/SSE/MCP).
Частые ошибки: смешение request/response направления; отсутствие назначения хедера.

## 10. Валидация входящих значений

Ожидается: таблица «Поле / Тип валидации / Правило / Сообщение / Код ошибки».
Частые ошибки: валидация без привязки к коду ошибки из раздела 8.

## 11. Безопасность и доступ

Ожидается: изменения ролей, permissions, аудита, PII/ПДн, шифрования.
Частые ошибки: молча «не меняется» без анализа; забытое разграничение доступа к новым полям.

## 12. Миграция

Ожидается: что мигрируется, стратегия (онлайн/офлайн), обратная совместимость API, rollback-план.
Частые ошибки: отсутствие rollback; скрипты миграции в теле change.md.

## 13. Логирование

Ожидается: новые/изменённые события с уровнем (по `common-requirements.md` раздел 1), кодом, форматом сообщения.
Частые ошибки: «добавить логи» без указания уровня и полей.

## 14. Мониторинг

Ожидается: новые метрики (имя, тип, теги), новые вычисляемые метрики (PromQL).
Частые ошибки: метрика без тегов; формула без описания семантики.

## 15. Изменения конфигурации

Ожидается: таблицы ADDED / MODIFIED / REMOVED параметров (имя, тип, значение по умолчанию, описание, обязательность).
Частые ошибки: yaml/properties-блоки целиком — запрещено; только таблица.

## 16. Рекомендации к критериям приёмки

Ожидается: сценарии в формате КОГДА/ТОГДА. Каждый новый/изменённый переход FSM (раздел 5) и каждый новый/изменённый инвариант (раздел 4) ДОЛЖНЫ иметь хотя бы один критерий приёмки.
Частые ошибки: unit-тесты/код тестов внутри — запрещено; должны быть поведенческие сценарии; пропуск покрытия для FSM/инвариантов.
Формат: см. «16. Рекомендации к критериям приёмки» в `change-examples.md`.

---

## Большие файлы

Change.md может получиться объёмным (200+ строк). Если файл большой — записывай его **по частям** (раздел за разделом), чтобы не потерять контент из-за ограничений контекстного окна. Предупреди пользователя: «Change объёмный, записываю по частям».

## Структура

- `openspec/specs/<service-name>/<service-name>.md` — актуальная спецификация сервиса (source of truth).
- `openspec/changes/<name>/` — активные change-запросы:
  - `change.md` — предложение системного аналитика;
  - `design.md` — технический проект (опционально для простых CR);
  - `tasks.md` — план задач на реализацию.
- `openspec/changes/archive/YYYY-MM-DD-<name>/` — завершённые change-запросы.

Директории создаются самими скиллами через `mkdir -p` — отдельный bootstrap не требуется.

## Скиллы

| Скилл                     | Назначение                                                                                     |
|---------------------------|------------------------------------------------------------------------------------------------|
| `openspec-teach`          | Этот учебник                                                                                   |
| `openspec-explore`        | Structured research кодовой базы: параллельные read-only субагенты по ролям (api/data/integrations/…), агрегация в `openspec/**/.research/`. Standalone — прямой вызов для разового картирования. Также работает prompt-library для `new-spec` / `propose` (они переиспользуют `openspec-explore/references/research-roles.md` и `openspec-explore/references/invocation-contract.md`, оркестрируя субагентов сами) |
| `openspec-new-spec`       | Создать спецификацию сервиса с нуля                                                            |
| `openspec-propose`        | Создать `change.md` (статус `На согласовании`)                                                 |
| `openspec-design`         | Создать `design.md` + `tasks.md` из согласованного change                                      |
| `openspec-implement`      | Выполнить `tasks.md`; обязательная верификация (сборка/тесты/линтер) перед объявлением готовности |
| `openspec-apply-change`   | Влить `change.md` в `spec.md` (откат — через git)                                              |
| `openspec-archive-change` | Переместить change в `archive/YYYY-MM-DD-<name>/`                                              |

## Жизненный цикл изменения

1. **Первая спецификация сервиса** — скилл `openspec-new-spec`.
2. **Предложение на изменение** — `openspec-propose` создаёт `change.md` (статус `На согласовании`).
3. **Ревью и согласование** — merge PR, статус вручную меняется на `Согласовано`.
4. **Технический проект** — `openspec-design` создаёт `design.md` + `tasks.md` (для сложных CR).
5. **Реализация** — `openspec-implement` выполняет задачи из `tasks.md`, ставит статус `В реализации`, по завершении запускает верификацию (сборка/тесты/линтер).
6. **Влитие в спецификацию** — `openspec-apply-change` мержит `change.md` в целевой `spec.md`, ставит статус `Реализовано`.
7. **Архивация** — `openspec-archive-change` перемещает change в `archive/YYYY-MM-DD-<name>/`. Если статус был `Реализовано` — меняется на `Архивировано`. Если другой (архивация «с warning») — физически перемещается, но статус в шапке сохраняется как был, для аудита незавершённой работы.

## Статусы change.md

| Статус          | Кто ставит                  | Когда                                                                                                                                                     |
|-----------------|-----------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| На согласовании | `openspec-propose`          | Change создан, идёт ревью в PR                                                                                                                            |
| Согласовано     | Аналитик вручную            | PR с change.md вмержен, change одобрен                                                                                                                    |
| В реализации    | `openspec-implement`        | Первый запуск implement, идёт кодинг по tasks.md                                                                                                          |
| Реализовано     | `openspec-apply-change`     | Изменения вмержены в спецификацию                                                                                                                         |
| Архивировано    | `openspec-archive-change`   | Change перемещён в архив из статуса `Реализовано`. При архивации с warning (другой статус) — физически перемещено, но статус в шапке сохранён для аудита |

Обратные переходы (например, возврат из `В реализации` в `Согласовано` для правок) — только вручную.

## Резолв путей bundle

Скилы OpenSpec ссылаются на собственные `templates/*` и `references/*` — файлы рядом с их SKILL.md. Пути в SKILL.md всегда относительные к директории своего скила.

По Agent Skills Spec runtime должен передавать абсолютный путь skill-директории в обёртке активации (строка `Skill directory: <abs-path>`). Если эта строка не передана — один раз `Glob("**/openspec-skills/skills/<skill-name>/<file>")` и бери первый результат. Пусто → спроси пользователя путь установки, не ищи вручную по `~`/cwd.

## Правила для агента

- **Не редактируй спецификации сервисов напрямую** — любое изменение оформляется через `change.md` + ревью.
- **Откат в apply-change — через git** (`git checkout HEAD -- <spec>`), не через `.bak`-файлы.
- **Верификация в implement обязательна** — запуск сборки/тестов/линтера перед объявлением реализации завершённой.
- **Проси подтверждение** через AskUserQuestion tool при неоднозначных ситуациях (нечёткий статус, несколько активных changes, несколько git-репозиториев рядом). Если AskUserQuestion недоступен в клиенте — задай тот же вопрос обычным текстом в ответе и дождись ответа пользователя перед продолжением. Не угадывай.
- **Не копируй примеры из шаблонов** в итоговые файлы — используй как ориентир формата.
- **Для размытого обсуждения/обдумывания** — используй обычный чат **без скила**. Conversational-режим в `explore` отключён.
- **`openspec-explore` standalone — с чёткими параметрами** (`target=spec|change`, `service`, `anchor` для change). Напрямую — только для разового картирования сервиса или зоны изменения. Внутри `new-spec`/`propose` его код не запускается — эти скилы переиспользуют его references-файлы и оркестрируют субагентов сами.
- **Tool запуска субагента** — имя и `subagent_type` зависят от harness'а и регистрочувствительны. Таблица известных имён + алгоритм обнаружения (регекс по списку доступных инструментов) — в `openspec-explore/references/invocation-contract.md § 3.1`. `task_id` не используется — запуск one-shot.

## Приоритет инструментов анализа кода

От наиболее семантического к наименее:

1. **Serena (MCP)** — `find_symbol`, `get_symbols_overview`, `find_referencing_symbols`. Семантический анализ, точная навигация по символам.
2. **LSP-инструменты** — go-to-definition, find-references, workspace symbols (если поднят языковой сервер).
3. **Code index / embeddings** — семантический поиск по кодовой базе.
4. **Другие MCP-серверы** — любые специализированные инструменты анализа.
5. **Grep / Glob** — текстовый поиск. Последний вариант, когда семантика недоступна.

Не ограничивайся чтением отдельных файлов — строй полную картину: зависимости, вызывающий код, связанные сущности.

## Маппинг запросов пользователя на скилл

Слушай формулировки пользователя и **проактивно предлагай соответствующий скилл** (или сразу запускай, если однозначно). Примеры — не исчерпывающий список, ориентируйся на смысл.

| Скилл                     | Триггер-формулировки пользователя                                                                                                                                                          |
|---------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `openspec-new-spec`       | «напиши/опиши спецификацию сервиса», «задокументируй сервис X», «нужна спека на Y», «давай опишем новый сервис», «составь документ аналитика для Z»                                         |
| `openspec-propose`        | «давай добавим/поменяем/изменим/уберём X в сервисе Y», «нужно обновить спеку Y», «внеси изменение Z», «предлагаю переделать W», «оформим CR», «сделаем change-запрос»                        |
| `openspec-design`         | «давай планировать реализацию», «нужен техпроект/дизайн», «распиши задачи», «сделай план разработки», «подготовь tasks.md», «спроектируй как это делать»                                     |
| `openspec-implement`      | «давай кодить/реализовывать», «выполни задачи из tasks», «пиши код по плану», «реализуй change», «делай то что в tasks.md»                                                                   |
| `openspec-apply-change`   | «влей change в спеку», «обнови спецификацию по изменению», «смержи change в spec», «применить change к спеке», «зафиксируй изменение в основной спецификации»                                |
| `openspec-archive-change` | «заархивируй change», «перенеси в архив», «убери change в archive/»                                                                                                                        |
| `openspec-explore`        | «картируй сервис X», «structured research по сервису», «research codebase», «собери карту зоны изменения» — всегда с явными параметрами (target + service [+ anchor])                       |
| `openspec-teach`          | «как работает openspec?», «научи пользоваться», «что за процесс?», «объясни workflow», «какой скилл использовать?»                                                                         |

**Правила маппинга:**

- «Новый сервис/документ с нуля» → `new-spec`. «Правка существующего сервиса» → `propose`. Не путай.
- Если есть согласованный `change.md` и пользователь говорит «пора кодить» — проверь наличие `design.md`/`tasks.md`. Нет — `design`. Есть — `implement`.
- Если пользователь сомневается / формулирует вопрос неопределённо — уточни через AskUserQuestion, а не угадывай.
- Запросы вида «посмотри», «изучи», «обдумай», «обсудим варианты» — это **обычный чат без скила**, не `explore`. `explore` запускается standalone только для structured research с явными параметрами. Внутри `new-spec`/`propose` — не запускается как отдельный скил, они работают с его references-файлами напрямую.
- Если пользователь говорит «давай делать X», но в проекте нет ни одной спецификации в `openspec/specs/` — скорее всего нужен сначала `new-spec`.

## Следующий шаг

Подскажи пользователю подходящий скилл исходя из текущего состояния проекта:

- нет ни одной спецификации сервиса в /openspec → `openspec-new-spec`;
- нужно оформить изменение существующей спецификации → `openspec-propose`;
- нужно получить разовую карту сервиса или зоны изменения (с параметрами) → standalone `openspec-explore` (NB: внутри `new-spec`/`propose` ресеч идёт через переиспользование его references, не через повторный запуск скила);
- есть согласованный change, пора проектировать → `openspec-design`;
- готов `tasks.md`, пора кодить → `openspec-implement`;
- реализация вмержена, пора обновить спецификацию → `openspec-apply-change`;
- change реализован и влит, пора архивировать → `openspec-archive-change`.
