Влить изменения из `change.md` в основную спецификацию (Analyst Merge).

**Input**: Опционально — имя change. Если не указано, определить автоматически или предложить выбор.

**Bundle-пути.** `references/X` — относительно директории этого скила. Если harness даёт строку `Skill directory: <abs>` в обёртке активации — используй её. Иначе один раз `Glob("**/openspec-skills/skills/openspec-apply-change/references/<file>")` и возьми первый результат. Пусто → спроси пользователя путь установки, не ищи вручную.

**Bundled materials** (относительно этого SKILL.md):

- `references/merge-workflow.md` — детальная механика мержа: таблица соответствия разделов, перенумерация, пересборка TOC, семантический diff заголовков, правила отката через git, форматирование HTML-разметки.

**AskUserQuestion fallback**: если инструмент недоступен в клиенте — задай тот же вопрос обычным текстом и дождись ответа пользователя. Не угадывай.

## Steps

### 1. Выбрать change

Если имя указано — использовать. Иначе:

```bash
ls openspec/changes/ 2>/dev/null
```

- Один активный change (исключая `archive/`) → автовыбор.
- Несколько → выбор через **AskUserQuestion tool**.

Объяви: `Применяю change: <name>`.

### 2. Проверь наличие change.md и его статус

Прочитай `openspec/changes/<name>/change.md`.

**Если файл не существует** → предложи сначала запустить `openspec-propose`.

Проверь поле `> **Статус**:` в шапке:

| Статус | Действие |
|--------|----------|
| `Согласовано` / `В реализации` | OK, можно мержить |
| `На согласовании` | **БЛОК**: change не согласован. Попроси дождаться merge PR и ручной установки статуса `Согласовано`. Выйди. |
| `Реализовано` | Поздравь, предложи запустить `openspec-archive-change`. Выйди. |
| `Архивировано` | Сообщи, что change уже заархивирован. Выйди. |
| Другой / отсутствует | Предупреди и спроси подтверждение через **AskUserQuestion tool**. |

### 3. Прочитай контекст

Прочитай:
- `openspec/changes/<name>/change.md` (полностью).
- Целевую спецификацию — путь из шапки change.md, поле «Целевая спецификация».

Если поле пустое или файл спеки не существует:

- Пустое / `отсутствует` → предложи через AskUserQuestion: (a) запустить `openspec-new-spec` для создания спеки сначала и потом вернуться сюда, (b) указать путь вручную. По умолчанию — (a).
- Указан, но файл не существует → сообщи пользователю о рассинхроне: в change.md указан путь, но файла нет. Предложи исправить путь или создать спеку.

### 4. Проверь git-состояние целевой спеки

Точка отката — через git, не через `.bak`. Запусти:

```bash
git status --porcelain <spec-path>
```

- Файл имеет незакоммиченные изменения → попроси пользователя сначала закоммитить или откатить. Выйди.
- Файл чист → продолжай. Точка отката лежит в `HEAD`.

Детали — `references/merge-workflow.md § 1`. `.bak`-файлы создавать запрещено.

### 5. Мерж разделов change.md → спецификация

Для каждого раздела change.md, значение которого **не** `Нет изменений.`, найди соответствующий раздел в спеке **по названию, не по номеру**.

Полная таблица соответствия разделов, правила перенумерации подразделов, пересборка TOC, сохранение HTML-разметки — `references/merge-workflow.md § 2–6`.

Порядок операций:

1. Найди целевой раздел по названию. Если нет — создай в логически подходящем месте (порядок секций в шаблоне спеки — ориентир; см. `merge-workflow.md § 3` с примерами иерархии разделов).
2. Вставь контент change.md в раздел.
3. Перенумеруй все подразделы в затронутой секции.
4. Обнови внутренние ссылки (`см. п. X.Y`).
5. Пересобери TOC по всем заголовкам.
6. Инкрементируй версию спеки в шапке (напр. `1.0` → `1.1`).
7. **Сохраняй** существующий контент, не затронутый изменением.
8. **Сохраняй** HTML-разметку (цветовые маркеры `<font>...`) в тексте спеки.

### 6. Обнови статус change.md

Замени строку `> **Статус**:` в шапке на:

```
> **Статус**: Реализовано
```

Меняй ТОЛЬКО эту строку.

### 7. Запиши обновлённую спецификацию

Сохрани весь результат шага 5 (мерж разделов + обновлённый TOC + инкремент версии) **одной записью** по пути `<spec-path>` (поле «Целевая спецификация» из шапки change.md). Шаг 6 — отдельное редактирование `change.md`, не смешивай с записью спеки.

### 8. Проверь мерж — семантический diff заголовков

Используй временные файлы **внутри репозитория** (не `/tmp`) — так портируется на любой POSIX shell, включая окружения без доступа к `/tmp`:

```bash
git show HEAD:<spec-path> | grep -E '^(##|###|####) ' > .headings-before.tmp
grep -E '^(##|###|####) ' <spec-path> > .headings-after.tmp
diff .headings-before.tmp .headings-after.tmp
rm -f .headings-before.tmp .headings-after.tmp
```

Детали альтернатив и process substitution — `references/merge-workflow.md § 7`.

Убедись:
- Ни один заголовок `##/###/####` из `HEAD` не исчез (кроме REMOVED-секций).
- Нумерация подразделов последовательная.
- TOC соответствует фактическим заголовкам.
- Внутренние ссылки (`см. п. X.Y`) валидны.

Если проверка провалилась — откати через `git checkout HEAD -- <spec-path>`, исправь, повтори.


## Guardrails

- ВСЕГДА читай change.md и целевую спецификацию перед началом.
- ВСЕГДА проверяй чистоту git-состояния спеки перед мержем — точка отката в `HEAD`, не в `.bak`.
- НИКОГДА не удаляй контент, не упомянутый в change (кроме явных REMOVED-секций).
- НИКОГДА не создавай `.bak`-файлы в репозитории.
- Проверяй семантический diff заголовков после мержа, а не только line count.
- Показывай что было сделано в итоге.

# Merge-workflow: подробности Analyst Merge

Детальная механика мержа `change.md` в целевую спецификацию сервиса. Высокоуровневый workflow — в `SKILL.md`. Здесь — правила, таблицы, команды.

---

## 1. Точка отката — git, не `.bak`

Перед мержем проверь чистоту git-состояния целевой спеки:

```bash
git status --porcelain <spec-path>
```

- Файл имеет незакоммиченные изменения → попроси пользователя сначала закоммитить или откатить их. Иначе мерж смешает их с результатом apply, откат станет невозможен.
- Файл чист → продолжай. Текущий commit в `HEAD` и есть точка отката.

**Не создавай `.bak`-файлы.** Если пользователь хочет сравнить до/после — пусть использует `git diff <spec-path>` или `git show HEAD:<spec-path>`.

Откат после мержа: `git checkout HEAD -- <spec-path>`.

---

## 2. Таблица «раздел change.md → целевой раздел спеки»

**Важно**: находи целевой раздел **по названию**, не по номеру. Нумерация в спеке может отличаться от change.md.

| Раздел change.md | Целевой раздел спецификации (по названию) |
|------------------|-------------------------------------------|
| 2. Бизнес-логика | Бизнес-правила и логика обработки |
| 3. Глоссарий (ADDED) | Глоссарий доменных терминов — добавить строки |
| 3. Глоссарий (MODIFIED) | Глоссарий доменных терминов — обновить определения |
| 3. Глоссарий (REMOVED) | Глоссарий доменных терминов — удалить строки |
| 4. Бизнес-инварианты (ADDED) | Бизнес-инварианты — добавить пункты |
| 4. Бизнес-инварианты (MODIFIED) | Бизнес-инварианты — обновить формулировки |
| 4. Бизнес-инварианты (REMOVED) | Бизнес-инварианты — удалить пункты |
| 5. Состояния и переходы FSM (ADDED) | Состояния и переходы (FSM) — добавить состояния/переходы |
| 5. Состояния и переходы FSM (MODIFIED) | Состояния и переходы (FSM) — обновить переходы/триггеры |
| 5. Состояния и переходы FSM (REMOVED) | Состояния и переходы (FSM) — удалить переходы/состояния |
| 5. Запрещённые переходы | Состояния и переходы (FSM) — обновить блок «Запрещённые переходы» |
| 6. Модели данных (ADDED) | Модели данных — добавить новые |
| 6. Модели данных (MODIFIED) | Модели данных — обновить существующие |
| 6. Модели данных (REMOVED) | Модели данных — удалить |
| 7. Интеграции | Интеграции |
| 8. Обработка ошибок | Обработка ошибок |
| 9. Хедеры | Хедеры и метаданные |
| 10. Валидация | Валидация входящих значений |
| 11. Безопасность | Безопасность (раздел 4.1) |
| 12. Миграция | Если одноразовая — оставить в change.md. Если меняет схему — в «Модели данных» |
| 13. Логирование | Логирование |
| 14. Мониторинг | Мониторинг (раздел 4.4) |
| 15. Конфигурация | Требования к конфигурационному файлу |
| 16. Рекомендации к критериям приёмки | Рекомендации к критериям приёмки |

Если целевой раздел не найден в спецификации — создай его в логически подходящем месте.

Разделы change.md со значением `Нет изменений.` **пропускаются**.

---

## 3. Перенумерация подразделов

После вставки новых подразделов **ОБЯЗАТЕЛЬНО** перенумеруй ВСЕ подразделы в затронутых секциях, чтобы нумерация была последовательной.

Пример: в секции 2.3 было 2.3.1–2.3.7, добавили 3 новых подраздела после 2.3.2. Итоговая нумерация должна быть 2.3.1–2.3.10. НЕ 2.3.1, 2.3.2, 2.3.8, 2.3.9, 2.3.10, 2.3.3, ….

Правила:

- Новые подразделы вставляются в логически правильное место (рядом с тематически близкими).
- Все последующие подразделы перенумеровываются.
- Все внутренние ссылки (`см. п. 2.3.2`) обновляются на новые номера.

---

## 4. Пересборка TOC

После мержа ОБЯЗАТЕЛЬНО обнови блок `<!-- TOC --> ... <!-- TOC -->` в начале файла.

Правила пересборки:

- Просканируй ВСЕ заголовки `##`, `###`, `####` в файле.
- Для каждого заголовка сгенерируй markdown-ссылку с якорем.
- Якорь: lowercase, пробелы → `-`, удаляются спецсимволы.
- Уровни вложенности: `##` без отступа, `###` с 2 пробелами, `####` с 4 пробелами.
- Сохраняй HTML-теги (напр. `<font>`) в тексте ссылки, но НЕ в якоре.

Формат строки TOC:

```
* [2.3.8. Правила классификации email bounce](#238-правила-классификации-email-bounce)
```

---

## 5. Версия спеки

**Инкрементируй версию** спецификации в шапке (напр. `1.0` → `1.1`).

---

## 6. Форматирование

При мерже **сохраняй HTML-разметку** в исходном тексте спеки:

- Цветовые маркеры: `<font color="red">**Alt**</font>`, `<font color="blue">**Opt**</font>`, `<font color="green">**Примечание:**</font>`.
- Прочие HTML-теги в тексте спецификации.

Не теряй их при вставке нового контента.

## 6.1. Перекрёстные ссылки и инварианты

При мерже разделов 3 (Глоссарий), 4 (Бизнес-инварианты), 5 (FSM) из change.md:

- Ссылки на правила из guard в FSM (`см. правило 2.X`) обновляй на актуальную нумерацию правил в спеке после перенумерации (§ 3).
- Если новый инвариант (раздел 4) имеет в change.md колонку «Покрывающий критерий приёмки» — проверь, что соответствующая строка добавлена в раздел «Рекомендации к критериям приёмки» (раздел 3 спеки) и ссылка валидна.
- Если новый переход FSM (раздел 5) имеет покрытие в критериях приёмки (раздел 16 change.md → раздел 3 спеки) — проверь ссылку на номер перехода `2.4.X`.
- Удалённые инварианты / переходы → найди в спеке все ссылки `см. инвариант 1.3.X` / `см. переход 2.4.X` на удалённые номера, отметь как «требуют ручной правки» в Output (не пытайся переписать автоматически).

## 7. Семантический diff заголовков (финальная проверка)

Команда через process substitution (bash в Linux/macOS):

```bash
diff \
  <(git show HEAD:<spec-path> | grep -E '^(##|###|####) ') \
  <(grep -E '^(##|###|####) ' <spec-path>)
```

Если shell не поддерживает process substitution (старый `sh`, Windows `cmd` без Git Bash) — используй временные файлы **в директории репо**, не в `/tmp`, и удали после проверки:

```bash
git show HEAD:<spec-path> | grep -E '^(##|###|####) ' > .headings-before.tmp
grep -E '^(##|###|####) ' <spec-path> > .headings-after.tmp
diff .headings-before.tmp .headings-after.tmp
rm -f .headings-before.tmp .headings-after.tmp
```

Убедись:

- **Ни один заголовок `##/###/####` из `HEAD` не исчез** (кроме явно указанных в REMOVED-секциях change.md). Переформулирование допустимо, исчезновение без REMOVED — запрещено.
- Нумерация подразделов последовательная (нет пропусков или дублей).
- TOC соответствует фактическим заголовкам.
- Все внутренние ссылки (`см. п. X.Y`) указывают на существующие номера.

## 8. Статус change.md после мержа

Обнови шапку change.md:

```
> **Статус**: Реализовано
```

Меняй ТОЛЬКО строку со статусом, остальное не трогай.

## 9. Что НЕ делать

- НЕ удаляй существующий контент, не упомянутый в change (кроме явных REMOVED-секций).
- НЕ создавай `.bak`-файлы.
- НЕ проверяй мерж по line count — только семантический diff заголовков (§ 7).
- НЕ привязывайся к номерам разделов — используй ТЕКУЩУЮ нумерацию и структуру целевой спецификации.
